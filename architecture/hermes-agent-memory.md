## 3. B. Replace/remove, deletes and the audit trail (rulings 4 and 5: as designed, no helper)
- Decision (ruling 5): no sweep, wrapper, scheduled job or new hq code. Hermes runs as designed with only the section 2 modifications and the curator-off line (section 11, A).
- Designed behaviour that remains (accepted): the automatic background reviewer's `replace`/`remove` of memory is STAGED by `_background_delete_gate` (`tools/memory_tool.py:171-189`; staging to `:210`). It fires only when `is_unattended_review()` (`tools/skill_provenance.py:43-44`); the only bypass is an attended `/refine` fork (`agent/background_review.py:1146-1150`). The docs say this is intended (`website/docs/user-guide/features/memory.md:319`). Staged edits wait until someone runs `/memory approve all` or `/memory approve <id>` interactively (`hermes_cli/write_approval_commands.py:49-50,71-72`); optional, never scheduled by us. An approve applies only to the exact staged entry and is refused if it changed since (`memory_tool.py:326-340`). The pending-store path name is UNVERIFIED.
- Unstaged paths: the foreground agent, and so any API door turn or a prompt-injected turn, applies memory `replace`/`remove` directly with `write_approval` false (the gate covers only unattended forks). A foreground skill delete is a hard `shutil.rmtree`; only background-review deletes are archived (`tools/skill_manager_tool.py:580-593`). api_server and cron paths: UNVERIFIED (probe D2, W3).
- Built-in audit trail (MEASURED): `skills.ledger` default true appends every skill mutation with before/after hashes to `skills/.curator_ledger.jsonl`, powers `hermes curator ledger` and `curator rollback <entry-id>` (`config_defaults.py:1482-1487`; `tools/skill_ledger.py:4`), capped at 5 MB (`config_defaults.py:1491`). No memory ledger was seen: UNVERIFIED that none exists. Because neither staging nor the ledger covers memory replace/remove, Hermes's own files on disk (section 7) are all there is for `memories/`.
- Consequence: staged background edits do not take effect until approved; memory grows by `add` and foreground edits meanwhile, bounded by the 2200-char cap.

## 4. C. All learnings live in Hermes: skills are the store
- Built-in memory (~3.5k chars) cannot hold hq's learnings. Measured today (`git ls-files`, bytes): `learnings/` 81 files / 672,209 B (includes `README.md` and `METHODOLOGY.md`); `retros/` 35 / 496,460 B; `decisions/` 54 / 659,216 B (not moved).
- Design (brain default under R-q): skills created by a one-time import script, plus the digest as the interim read path until the import is verified. Skills are the store; the `hq-index` skill keeps tools/architecture pointers only and drops per-learning lines (they would duplicate Hermes's own skills index).
- **Hermes's skills index (MEASURED, read-only source, T-470 row 5 fix):** every skill gets one line in the system prompt each session, `    - <name>: <description>` under its category (`agent/prompt_builder.py:1476-1494`), but the description there is CUT: the builder takes it from `extract_skill_description` (`agent/prompt_builder.py:1283-1291`, called for the scan at `:1416` and `:1548`), which keeps the first 57 characters plus "..." when the description is longer than 60 (`agent/skill_utils.py:822,831-834`). The render step prints whatever it is handed and does no cutting of its own (`:1442-1494`). The full description (up to 1024 chars) reaches the model only through `skills_list` (`tools/skills_tool.py:212-218,239`, cut at 1024 by `tools/skills_tool_plugin.py:16,39-42`) and `skill_view` (`tools/skills_tool.py:636`, the frontmatter value as written). Entries are never dropped, but a "demoted" category collapses to a names-only line (`:1442-1469`; what demotes is UNVERIFIED). The prompt says to load any skill "even partially relevant". So findability rests on the first 57 characters of each description: the import script puts the title and routing text first and kind, category and date last. The 1024 cap and the 100,000-char body cap are in `tools/skill_manager_tool.py:109-110`. Cost: with the 116 skills the script imports, the index is about 12,000 characters, about 4,400 tokens at 2.75 chars per token (scaled linearly from an 11,600-character scratch estimate for the earlier set, not re-measured) (`tools/skill_manager_tool.py:110`), every session; the bodies cost nothing until loaded. That estimate is derived from a scratch import, not measured in a live prompt (probe L1).
- **Import script design (deliverable 5):** one skill folder per file, with a generated real description (what the learning is and when it applies; not the first `#` heading), hq's topic folders kept as skill categories, and text, date, origin `path@sha` in the body. Of the 116 files (81 + 35), 11 exceed 24,000 bytes; the largest is `retros/2026-07-model-tier-policy-eval.md` at 74,521 B; none exceeds the 100,000 cap (MEASURED). All 116 files are imported (81 learnings + 35 retros; decisions C and D, section 11), including `README.md`, `METHODOLOGY.md`, `retros/README.md` and `retros/_TEMPLATE.md`. Import naming (merged at `26baf333`, PR #45): the four generic files are imported under category-prefixed names, `learnings-readme`, `learnings-methodology`, `retros-readme`, `retros-template`, via an exact full-path map in `tools/hermes/il_describe.py` `skill_name()`. The script takes a target-dir argument and REFUSES `h1-home` unless the owner passes it (section 9).
- **Curator (MEASURED; OFF by the owner's word):** the source default is `enabled: True` (`config_defaults.py:1498-1499`); the owner decided on 2026-10-13 to turn it off (`curator.enabled` false, decision A, section 11), and `agent/curator.py:106-107,164` gates every run on that key. So the curator marks nothing stale and archives no Hermes-written skill (the source defaults it would otherwise apply are 14 unused days stale and 30 archive: `config_defaults.py:1502-1503`). The skills ledger and `curator rollback` are unaffected: they gate on `skills.ledger` (`tools/skill_ledger.py:113-115`; `config_defaults.py:1487`), which `skill_ledger.py` does not tie to `curator.enabled`. Skills without `created_by: agent` were never managed (`tools/skill_usage.py:1-6,292-297`). The config line is row 13 (section 9); an agent does not apply it.
- Not investigated (owner: no more broad investigation), kept as probes: how a large skill set loads and searches; whether API turns persist to `state.db` and `session_search`.
- `decisions/` stays in hq. The import of all 116 files, retros included, is decided (decisions C and D, section 11); the removal of `learnings/` and `retros/` from hq is a separate step and stays OWNER-GATED.

Inside Hermes, skills are procedures it follows itself, and its guard scanner and SOUL.md bound that. If a memory or skill conflicts with hq git tools or architecture, hq git wins.
