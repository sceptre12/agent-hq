# Migration Assessment

## Trigger

Use when any skill needs to assess whether a described change to `de-foundations`
requires a new migration script for `dft-mfe-generator` or `dft-web-monorepo-generator`.

Known callers: `pr-check-migration-needed` (PR context) and `jira-ticket-quality`
(ticket context). You don't need either caller's definition to run this skill —
the logic here is self-contained; callers only supply the three inputs below.
This skill runs at whatever model tier the caller runs at.

## Inputs (supplied by the caller)

- `context_type`: `pr_diff` | `ticket_description` | `plain_text`
- `changes_description`: the text to assess (diff, ticket summary, or free-form)
- `package_scope`: `mfe-generator` | `web-monorepo-generator` | `both` | `unknown`

`context_type` only tells you how to read `changes_description` (a code diff, a
ticket summary, or free-form text). The checklist logic in Step 1 is identical
for all three.

## Steps

1. **Apply the trigger checklists.** For each package in scope, scan
   `changes_description` against the relevant checklist. One YES = migration needed
   for that package. A trigger fires only on affirmative evidence in
   `changes_description` — never on speculation about what a change *might* also
   touch. If the description is too sparse to rule a trigger in or out, do not
   guess: leave it unfired and name it in the verdict's Reason as "could not
   evaluate".

   **MFE Generator triggers** (apply when scope is `mfe-generator`, `both`, or `unknown`):

   | # | Trigger | Why it needs a migration |
   |---|---------|--------------------------|
   | M1 | New field added to generated `mf-config.ts` | Existing consumer files lack the field |
   | M2 | Existing field removed or renamed in generated `mf-config.ts` | Consumer files have the old field; it may cause runtime errors |
   | M3 | New field added to generated `jest.config.js` / `jest.preset.js` | Existing files lack it |
   | M4 | Field removed or renamed in generated `jest.config.js` / `jest.preset.js` | Old field left behind in consumers |
   | M5 | New devDependency added to generated `package.json` | Consumers need it auto-installed |
   | M6 | Dependency version constraint changed in generated `package.json`, and existing consumer ranges don't already satisfy it | Consumers have the old range |
   | M7 | New generated file introduced (any file the generator writes) | Consumers don't have it yet |
   | M8 | Generated file removed from the template | Consumers still carry the old file |
   | M9 | `generator-version.json` schema changed | Existing version stamps need updating |
   | M10 | Shared utility in `src/shared/` changes its contract (function signature, exported type) | Existing migration scripts that call it may break at runtime |

   **Web Monorepo Generator triggers** (apply when scope is `web-monorepo-generator`, `both`, or `unknown`):

   | # | Trigger | Why it needs a migration |
   |---|---------|--------------------------|
   | W1 | New field added to generated `nx.json` | Consumers need it |
   | W2 | Field removed or renamed in generated `nx.json` | Consumers have old field |
   | W3 | Changes to generated `package.json` (new dep, removed dep, version change) | Consumers need auto-update |
   | W4 | Changes to CI/CD template files generated by the generator | Consumers carry stale CI config |
   | W5 | New generated file introduced | Consumers don't have it |
   | W6 | Generated file removed | Consumers still carry it |
   | W7 | `generator-version.json` schema changed | Version stamps need updating |
   | W8 | Health-fix logic added that consumers need applied | Existing workspaces didn't get the fix |
   | W9 | `known-repos.json` schema or structure changed | Consumers carry old format |

   **Non-triggering changes:** fixes inside existing migration scripts; test-only
   changes; documentation changes; refactors that don't change generated output;
   version bumps where existing consumer ranges already satisfy the new version (see
   M6); build config changes that don't affect generated output; new strictly
   opt-in generator options.

2. **Produce the verdict.** If no triggers fired:

   ```
   VERDICT: No migration needed

   Reason: [one paragraph explaining which triggers were examined and why none fired]
   Checked: [list trigger IDs, e.g. M1-M10, W1-W9]
   ```

   If triggers fired:

   ```
   VERDICT: Migration required

   Package(s): [dft-mfe-generator | dft-web-monorepo-generator | both]
   Triggered by: [M3, W5, ...] — [short label for each]
   Could not evaluate: [trigger IDs the description was too sparse to assess — omit this line if none]
   ```

   Then write the migration brief (step 3).

3. **Write the migration brief** (only when the verdict is "required") — one section
   per package that needs a migration:

   ```markdown
   ## Migration Brief — <package-name>

   ### What the migration must do
   **[Trigger ID] — [Short label]**
   - What changed: [one sentence]
   - What consumer files look like today: [example if possible]
   - What migration must transform it to: [example]
   - Implementation hint: [transformer pattern reference]
   - Test requirement: [one describe block]

   ### Manual steps (not automatable)
   [Any steps that can't be scripted]

   ### Acceptance criteria
   - [ ] tsc passes
   - [ ] All new spec tests pass
   - [ ] Idempotency test added for every transformer
   - [ ] migrations.json updated
   ```

## Red flags

| Rationalization | What to do instead |
|---|---|
| "The change is internal so no migration." | Check whether internal refactors change generated output. If the generator writes different bytes to consumer files, it needs a migration. |
| "It's a minor version bump." | Version number alone doesn't determine migration need — the content change does. |
| "There's already a migration for this." | Confirm by checking the exact field/file. Don't assume coverage. |
| "The Confluence guide says manual." | Manual steps still need to be called out in the brief even if they can't be scripted. |
| "The description is too sparse, I'll guess." | Leave the trigger unfired and name it "could not evaluate" in the verdict's Reason instead of guessing. |

## Exit criteria

- [ ] Every applicable trigger (M1-M10 and/or W1-W9, per `package_scope`) was checked
  against `changes_description`, not just the first match.
- [ ] A "Migration required" verdict names every triggered ID and its package; a "No
  migration needed" verdict names which triggers were examined.
- [ ] A required verdict is followed by a migration brief with all four subsections.
