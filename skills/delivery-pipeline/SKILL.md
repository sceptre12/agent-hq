## Trigger
Use when the owner wants a change carried end to end by an agent team, or says "run the delivery pipeline", "next stage" or "resume" (card 1, `architecture/delivery-workflow/part-02-skill-inventory.md`). This session is the conductor: design tier (`tools/model-routing.md`), depth 0, the only writer of `state.md`, the only launcher of `claude -p` leads. It never dispatches unit workers; the stage skills it hosts may dispatch their own agents (explorers, review seats, Plan-checker, capture and read-back agents). Model-invocable (D16).

Authority: INTERFACES 1.7.0 (`architecture/delivery-workflow/INTERFACES.md`; `interfaces/part-a-state.md` A.1-A.8, `part-b-desk.md` B1-B9, `part-c-waves-control.md` C2-C8, `part-d-enums-topics.md` D1-D3, D8; section line pointers in `references/provenance.md` §Sources); where this file differs, INTERFACES wins. Gate-file names carry the run id (A.2.1): `H0.ok` means `H0.<run-id>.ok`, likewise for every gate. Depth: `references/stages.md` (per stage), `references/tick-relay.md` (the 1-minute tick), `references/launcher.md`, `references/resume.md`, `references/stops-and-posts.md`. Templates: `references/templates/state-and-substate.md`, `retro-and-execution-log.md`, `artifact-to-plane.md` (read, never edit).

## Steps
0. **Step 0, inputs (D1, D2.2 row 1).** `DELIVERY_ROOT` is the environment variable only: unset prints `INPUT-ERROR DELIVERY_ROOT unset`; not `^/[^[:space:]]+$` prints `INPUT-ERROR DELIVERY_ROOT format`. Then exactly one of: `INTENT` (text) with `PRIMARY_REPO` (absolute path of the primary clone root; missing is `INPUT-ERROR PRIMARY_REPO missing`, not a directory is `... path`); or `RUN_HOME` (an existing directory under `$DELIVERY_ROOT` holding `state.md`). A bare argument naming such a directory is `RUN_HOME`; any other text is `INTENT`. Neither is `INPUT-ERROR INTENT missing`. A `RUN_HOME=` under `$DELIVERY_ROOT` with no `state.md` (`INPUT-ERROR RUN_HOME path`) or an unparsable one (`INPUT-ERROR RUN_HOME format`) is the card 1 missing-state stop: print that line, then the rebuild report derived from the row files (`references/resume.md`; printed, never written), write nothing, stop. Each failing field prints one `INPUT-ERROR <field> <reason>` line (`missing|enum|path|unset|format|sha`, D1; D8 29-9), then stop: no retry, no prompt, nothing written.
1. **ORCHESTRATOR-CHECK, before any write.** The Agent tool is present and this session is not a subagent (depth 0). On failure print `ORCHESTRATOR-CHECK FAIL <reason>` and stop.
2. **Resume (input `RUN_HOME`).** Follow `references/resume.md`, in its order: read `state.md` and check the version pins (a mismatch stops and reports); the B1 applied-result scan, before any send (own `RUN_HOME/desk/*.out` results the record lacks, `references/resume.md` step 4, 29-25; local writes only); a new own session token and machine row; re-arm the 1-minute relay tick; re-send every `REGISTER-SENDER` line of the run (`run` first; a `refused` waits for the human's `REBIND`, B8, and nothing else is sent before its `ok`, 29-27); re-attach own `.req` files without `.out` and re-send each `pm/outbox/*.conductor-request.sending-<id>` with the same `<id>`; inbox replay and the re-derivation of every due inbox message (rule R2); the dead-lead check over `released|building|pr-open` and `merged` not yet `cleaned`, where a launched sub-task is never launched twice under its token (R1); then continue at `stage` through its re-entry predicate (`references/resume.md` step 11, 29-17). A `RUN_HOME` whose `stage` is `done` or `stopped` is reported, not resumed.
3. **Stage 1, run setup and intake.** Mint the run-id (A.1): `<epic-key-lowercased>-<yyyymmdd>` only when the human names an existing epic, else the provisional `run-<n>-<yyyymmdd>` (`n` the first free integer under `$DELIVERY_ROOT` that day); a collision with a different epic appends `-2`, `-3`. A run-id is never renamed. Under `umask 077` create `RUN_HOME=$DELIVERY_ROOT/<run-id>` and `plans_dir` (`<PRIMARY_REPO>/plans/<epic>/`, or `plans/<run-id>/` for a provisional id; never renamed). Mint the own session token `<run-id>-c<n>` (`n` counts conductor sessions; `references/launcher.md` §Session token) and write the own machine row `machine/<session>.row` (`build=0`) under `mkdir $DELIVERY_ROOT/machine/.lock` (A.4, AM-4 W2-9). Write `state.md` first, atomically (temp file plus `mv`), one YAML document per the state template: `run_id`, `epic` (the named key or empty), `plans_dir`, `primary_repo`, `delivery_root`, `stage: 1`, `gates`, `subtasks: []`, `skill_versions` (`<version>@<sha256>` of each installed delivery `SKILL.md`, `ls -L` plus `shasum -a 256`), `interfaces_version` (`<version>@<sha256>` of the live `INTERFACES.md`, version read from that file, never copied from the A.2 example), `orchestrator_tier: design`, `security_audit: guidance`, `machine_ledger_row`. Claim the run at the desk: `REGISTER-SENDER <run-id> | run | <own sender-id>` to `desk` (B1) and arm the 1-minute relay tick (step 9) at once; the claim and its no-reply re-send are exempt from the send gate (R4, 29-27). On the tick that finds `REGISTERED <run-id> | run | ok` (`refused`: post and stop) invoke `delivery-intake` with `RUN_HOME`, `PLANS_DIR`, `PRIMARY_REPO`, `INTENT` (`DELIVERY_ROOT` in env). Copy its last stdout line `PROFILE: <path>@<sha>` into `repo_profile`. Post (step 13) with the H0 `GATE` line and end the turn; the tick records `RUN_HOME/gates/H0.ok` in `gates.H0`.
4. **Stage 2, architecture and H1.** Invoke `delivery-architecture` with `RUN_HOME`, `PLANS_DIR`, `REPO_PROFILE` (= `repo_profile`). Exit: `PLANS_DIR/review-architecture.md` line 1 `ARCH: ready`. Read the one required `security_sensitive: yes|no` line of `architecture.md`: a missing line is `INPUT-ERROR security_sensitive missing`, two lines or a value other than `yes|no` is `INPUT-ERROR security_sensitive format` (never read as `no`); set `security_audit: full` on `yes` or on an explicit operator request, else keep `guidance` (A.2, OQ-1). Post, then wait for exactly one live H1 file: `H1.ok` -> `gates.H1`, continue; `H1.changes` -> re-invoke `delivery-architecture` (the notes in `gates/H1.notes.md` bind), stay at stage 2, and record `h1_handled` (its name and `utc=`) only after the call returns; the old file stays live, so H1 is pending again only when the live file's name or `utc=` differs, and the stage 2 skip also needs `review-architecture.md` newer than that `utc=` (29-17); `H1.reject` -> write `stage: stopped`, post the stop naming `gates/H1.notes.md`, run `delivery-cleanup` `MODE=final` (abandoned run, C5.1), no `TICKET-EVENT` (no ticket exists); a new attempt is a new `INTENT`. After `H1.ok`, run `ticket-clerk` with `RUN_HOME`, `PLANS_DIR`. Its wave 1 is the epic `jira-create` with `<subtask>` `run`; the conductor sends no separate epic request. Copy the epic key (the `tickets.tsv` row whose `parent` is `-`) into `state.md` `epic`, and append `TICKET-EVENT <key> published` for each ticket created (D3). Run `ticket-clerk` again on the D62 cadence (loop hand-back or about every 30 minutes).
5. **Stage 3, dispatch plan.** Invoke `delivery-dispatch-plan` with `RUN_HOME`, `PLANS_DIR`, `REPO_PROFILE`. Exit: `RUN_HOME/plan-check.md` line 1 `PLAN-CHECK: clean`. `PLAN-CHECK: <n> findings` after round 3 is a D7 stop: post it with the path and wait for the owner; dispatch nothing; a resume re-posts it and re-invokes only on the owner's word, and a dispatch-plan stop without `plan-check.md` is posted the same way (29-34). A clean `plan-check.md` with `PLAN-REVIEW: STOP round-3` in the plan's review section is the same D7 stop (29-23, AM-6 (g)). On clean, add one `subtasks[]` entry per sub-task of the plan's table (`id`, `backend`, `state: planned`), post (no gate; the human is informed, Rule 11).
6. **Stage 4, launch leads.** A sub-task is ready (launch-ready) when it has no `depends-on` predecessor or every `depends-on` predecessor has `merge_sha` in `state.md` (R2, 29-14); a post-merge re-entry `st<N>` also needs its `dispatch-plan.md` row and a clean `plan-check.md` newer than `pm/new-units.md` (29-29). Merge order (`st0`, the plan PR, first) governs only the step 10 merge precondition, never a release (29-18). Before each launch, check the machine ledger under `machine/.lock` (`references/launcher.md`): a new lead counts 31 (30 slot and reserved agents plus its own seat), so a launch needs `sum(live_count) + 31 <= 200` (200 is D4; 31 and the build count are defaults, 29-2), where each live lead counts max(31, its row's `live_count`) until `CLEANUP DONE` or a dead pid, a live launch with no row yet 31, and the sub-task being (re)launched is left out (R1, 29-26, 29-38), and a `MODE=build` launch needs at most 2 `build=1` rows or live pending build launches (rule 8); else refuse and ask the human. Pass exactly the D2.2 row 6 inputs: `RUN_HOME`, `SUBTASK`, `MODE` (`plan-pr` for `st0`, `post-merge` for `pm`, else `build`), `BACKEND`, `PLANS_DIR`, `REPO_PROFILE`, `REPO` (the sub-task table `repo`; for `pm` `primary_repo`, its `BACKEND` the `st0` backend, and it runs in the detached post-merge worktree at the merge sha, never the main checkout, A.8 s7-4), `SESSION` (a fresh launcher session token `<run-id>-<subtask>-l<n>`, `n` the launch count for that sub-task), `PM_SHA` (`pm` only), `SECURITY_AUDIT` (= `security_audit`), `DELIVERY_ROOT` in env. `BACKEND=claude-p`: launch through the §6.4 launcher spec (`env -i` allowlist, scrubbed git/gh/ssh, asserted `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=30`, `--disallowedTools` per `references/launcher.md` (29-21), prompt on stdin; fail closed), in the sub-task worktree the conductor adds first (29-22). `BACKEND=agent-tool`: the owner starts the session; the status post gives the inputs and asks for it (C5.2). Only after every fail-closed check and the worktree add, write the launch intent (`session`, `launched_utc`, `state: released` for a sub-task released at launch, `relaunch_phase`) in one `state.md` write, then exec (R1, 29-26). A successor's `RELEASE` is written by the tick's re-derivation when due (R2).
7. **Inbox writes (C5.1, C6).** Every message is a file `RUN_HOME/<subtask>/inbox/<seq>-<yyyymmddThhmmssZ>-<type>.md`, `<seq>` allocated by an `O_EXCL` create of `inbox/.seq/<seq>`, line 1 the message verbatim: `RELEASE <subtask>`, `INVALIDATE <subtask> <reason>` (`<subtask>` is always the receiver; reason in `predecessor-reentered|predecessor-rebased|contract-changed|plan-changed`), `MERGED <subtask> <merge_sha>` (`^MERGED (st[0-9]+) ([0-9a-f]{40})$`). The inbox file is canonical; to an `agent-tool` lead a `SendMessage` may follow carrying only `INBOX <subtask>`.
8. **Back-edges.** A sub-task whose `substate.md` `phase` returns to `building` from `pr-open` or `merged` re-entered stage 4: write `state: building`, `reentered: true`, `reentered_utc` and clear its `merge_sha` in one write (29-25); the `INVALIDATE <successor> predecessor-reentered` files to each released successor then follow by re-derivation (R2), each with `TICKET-EVENT <key> blocked`; the fresh `RELEASE` follows by R2 once the predecessor re-merges, then `TICKET-EVENT <key> unblocked`. The other three reasons follow the same pause and release pattern (`references/stages.md`).
**Derivation rules (29-13..29-16, 29-25..29-27; `references/provenance.md`).** R1, launch intent after the fail-closed checks and before exec: `session` (its `-l<n>` is the stored launch count), `launched_utc`, the release and `relaunch_phase`; a launched sub-task is never started twice under that token, and counts in the ledger before its row exists only while live (`references/launcher.md`, 29-26). R2, due inbox messages are re-derived from `state.md` each tick and at resume, keyed on the current cycle (29-25): `RELEASE` (all `depends-on` predecessors merged; for `pm` every other sub-task merged and a launched `pm` entry) with no `release` file newer than the receiver's latest `invalidate` file or, for `pm`, its `launched_utc`; `MERGED` with no `merged` file naming the current `merge_sha`; `INVALIDATE` to a successor whose `released_utc` precedes the predecessor's `reentered_utc` and that has no `invalidate` file newer than it. Each is written once; no step remembers one (`references/tick-relay.md` §Inbox writes). R3, every wait is entered by printing the post and ending the turn, and every new stop, escalation, refusal, no-reply or human step is posted on the tick that finds it, not only at a gate post. R4, every conductor send (`REGISTER-SENDER`, own requests, relayed `CONDUCTOR-REQUEST`s) has the 5 + 5 minute no-reply rule (default) and a terminal `REJECTED` is posted; before `REGISTERED <run-id> | run | ok` no tick step or stage step, except the `run` `REGISTER-SENDER` claim and its re-send (29-27), sends to the desk, relays, renames, launches a lead or runs `ticket-clerk` (29-16; `references/tick-relay.md` step 0).

9. **The 1-minute relay tick (B1, C5.1; `references/tick-relay.md`).** The conductor arms only this tick (prompt `delivery-pipeline tick <RUN_HOME>`); the merged 10-minute tick is the lead's (C7). Each tick, file reads only, never a bus: (a) each `RUN_HOME/<subtask>/outbox/register` matching `^REGISTER ([a-z0-9-]+) (st[0-9]+|pm) ([^ ]+) ([a-z0-9-]+)$`: record `lead_id` and `session`; identity `-` writes no line and is renamed `register.consumed` at once; else send `REGISTER-SENDER <run-id> | <subtask> | <identity>` and rename `register.consumed` on `REGISTERED ... ok`, `register.refused` on `refused` (post it; the lead stops). (b) each `outbox/<id>.desk`: relay the `DESK` line to `desk` as sender and rename `<id>.desk.relayed`; a wrong `<subtask>` or a conductor-only verb (`pr-merge|publish|tag-push|test-report-push`) is never relayed: rename `<id>.desk.refused`, log and post it, write no stop row (`references/tick-relay.md` §2). (c) each `RUN_HOME/pm/outbox/<seq>.conductor-request`: a line not matching the C5.1 regex is renamed `.refused` and posted; else adopt or mint the request (R4), rename `.sending-<id>` before the send, send, rename `.sent-<id>` (`references/tick-relay.md` §3). (d) read each `substate.md` (`phase`, `prepr`, `head`, `pr`, `review_record`, `ci`, `stop_reason`, `postmerge`) and map it to `subtasks[].state` (`planned`, `released`, `building`, `pr-open`, `merged`, `stopped`, `cleaned`; A.2), forward only, the step 8 back-edge the one exception (29-37); `PREPR: PASS` appends `TICKET-EVENT <key> prepr-pass`, the first `phase: building` appends `dispatched` (`<key>`: the sub-task's dispatch-plan `ticket`, resolved through `tickets.tsv`, D3). (e) list `RUN_HOME/*/escalations/*.md` and the run-level `RUN_HOME/escalations/*.md` (C2); append `TICKET-EVENT <key> blocked` once per new file and list open ones in the next post. (f) dead-lead check (`references/tick-relay.md` §7; 29-13, 29-26): a lock older than `launched_utc` and a lead pid alive or launched under 10 minutes ago are skipped; a dead lock owner triggers the C5.3 relaunch (step 11); no pid 10 minutes after `launched_utc` is a startup failure (post `lead.log`, one relaunch); a `pm` with `postmerge: FAIL`, `POSTMERGE: STOP` or a terminal release is never relaunched (29-19). (g) read each `cleanup-<run-id>-<subtask>.md` line 1 `CLEANUP DONE <subtask>` -> `state: cleaned`. (h) record each new `RUN_HOME/<subtask>/gates/H-e2e.<subtask>.ok` in `gates.H-e2e`; the lead, not the conductor, waits on it before generation (A.2.1); until it exists the post gives the `GATE <run-id> H-e2e.<subtask> ok` line and the `.feature` list path. (i) R2 due messages; continue a stage whose gate file or exit token appeared; launch ready sub-tasks; run the 5b readiness check; append `TICKET-EVENT <key> unblocked` when the ticket's latest `ticket-events.log` event is `blocked` and no escalation, stop or `INVALIDATE` blocks it any more (29-15); post per R3. Also each tick: own `.out` polling, own machine row rewrite, ticket flush (`references/tick-relay.md` §4, §8, §9).
10. **Stage 5b, merge in plan order, one at a time.** The conductor's own desk verbs, all with `<subtask>` `run` (B1, B4): `pr-approval-state`, `pr-merge`, the epic `jira-create` (composed by `ticket-clerk` here), and the relayed `publish`, `tag-push`, `test-report-push`. Merge a sub-task only when it is `pr-open` with `merge_sha` empty (29-37) and its `substate.md` shows `pr` set, `ci: GREEN <sha>`, `prepr: PASS`, `head` = `<sha>` and `review_record` naming `record-<sha>.md` (AM-4 W2-7), and every merge-order predecessor (every sub-task with a lower dispatch-plan `merge order`, `st0` first; D5, 29-18) is `merged`, and no terminal `pr-merge` `REJECTED` or `.req.noreply` blocks this `head` (29-16). Request `pr-approval-state` `{repo, pr}`; on `h_pr: true` with `headRefOid` = `<sha>`, record the H-pr pointer `gh:<owner>/<repo>#<pr>@<commit_id>` in `gates.H-pr`, else post and keep waiting (H-pr is the human's). Then `pr-merge` `{repo, pr, subtask, method, expect_head, predecessors[], record_path}` with `<subtask>` `run`, `fields.subtask` `st<N>`, `method` the profile `merge_method`, `expect_head` `<sha>`, `predecessors[]` the merge-order predecessors' PR numbers, `record_path` = `review_record`; build each request with `desk-req.sh <run-id> run <verb> <fields-json-file>` and send the `DESK` line to `desk`. On `DONE`: write `RUN_HOME/merge-<merge_sha>.md` atomically (`pr=`, `merge_sha=`, `method=`, `merge_reach=` from the `.out`), set `merge_sha` and `state: merged`, write inbox `MERGED <subtask> <merge_sha>`; successors' `RELEASE` follow by R2. On `REJECTED`: post it, then its B2.1 class and resend trigger (`references/stops-and-posts.md` §Desk refusals, 29-33); never another channel. Never merge two at once.
11. **Stops and relaunch (A.3 `stop_reason`, AM-4 W2-5, A.8; `references/stops-and-posts.md`).** `stop-the-line:<row>`, `d7-round3` (also the lead's mapping of `CI: HUMAN d7-round3`), `human`, `port-refused` -> `subtasks[].state: stopped` (a `pm` `human` with no `POSTMERGE: STOP` record too, 29-31) and a post naming the open-finding paths (`RUN_HOME/review/<subtask>/`, `checklist-<subtask>.md`) or escalation paths, and for `human` always `homes/<session>/lead.log` and `substate.md` (default); `port-refused` names the sub-task and the port, and the conductor never picks a port. `TICKET-EVENT <key> blocked` only per D3: `d7-round3` here, escalations (9e), `INVALIDATE` (8); the other stops none of their own. Other sub-tasks continue (D7). `spawn-cap` and a dead lead (step 9f) keep the state and are C5.3 triggers: relaunch per `references/resume.md` §Lead relaunch (`claude-p`: once the old lock is gone or stale, brief `resume <subtask>: re-read substate.md, inbox/ and gates/` on stdin; `agent-tool`: the full call plus that brief in the post). A lead that dies again with `phase` still equal to `relaunch_phase` is reported to the owner (sub-task, both session tokens, `lead.log`, `substate.md` paths), not relaunched a third time; spawn-cap counts the same way. `invalidate` keeps the state (step 8). An `INPUT-ERROR` from a stage skill or reviewer is not a D7 round: fix the input and re-invoke with the same round count. A sub-task leaves `stopped` only via the desk-written `RUN_HOME/gates/RESUME.<subtask>.<run-id>.ok` (post `GATE <run-id> RESUME.<subtask> ok <text>`; A.8, B9), to its pre-stop phase (the desk clears `stop_reason`, INTERFACES 1.6.0 AM-6 (f)). `stale-session` (a second `pm` lead found a fresh lock; O-1 lead default) is posted, not relaunched. A `claude -p` lead's clean wait exit (CV47) is no death: relaunch it on its waking inbox file or next tick (`references/resume.md`).
12. **Stages 6-7, the `pm` host.** After the last sub-task merges, add `subtasks[]` `id: pm` (`repo` = `primary_repo`, `backend` = the `st0` backend, 29-19), launch it as step 6 with `MODE=post-merge`, `PM_SHA` = that last `merge_sha` and the `STAKES`/`CONTENTION`/`NOVELTY` lines 2-4 of `PLANS_DIR/review-architecture.md` appended to its prompt (29-28); its `RELEASE pm` follows by R2. Relay its `CONDUCTOR-REQUEST` lines (step 9c). Read `postmerge`, and while it is empty `RUN_HOME/postmerge-<pm_sha>.md` line 1: `POSTMERGE: STOP <reason>` is posted with the record path, no ticket event, wait; for a destructive row the post names the row and gives `GATE <run-id> H-destructive.<row-id> ok <text>` (desk-honoured; A.2.1, B9). `PASS` appends `TICKET-EVENT <key> verified`; `FAIL` is the post-merge re-entry, once per `pm_sha` (29-36): read `RUN_HOME/pm/new-units.md`, add `st<N>` (next free `N`, `state: planned`, `pm_sha`), re-invoke `delivery-dispatch-plan` with `NEW_UNITS=$RUN_HOME/pm/new-units.md`, name `st<N>`'s plan `ticket` in the post (29-20), continue at step 6 for `st<N>` once it is launch-ready (29-29); when `st<N>` merges, a second `pm` lead starts with `PM_SHA` = that `merge_sha` under the entry-reuse, lock and old-worktree rules of `references/stages.md` stages 6-7 (29-5, O-1; 29-19). Read `release_record` line 1: `RELEASE: WAITING-HUMAN` is posted with the release steps awaiting `GATE <run-id> H-prod.<step_id> ok`; record each `gates/H-prod.<step_id>.ok` path in `gates.H-prod`. `RELEASE: LIVE` or `RELEASE: ROLLED-BACK` is terminal; the `pm` lead then runs its own cleanup (`CLEANUP DONE pm`, counted only with a terminal release and a record newer than the current `pm` `launched_utc`, 29-32).
13. **Status post and end of turn.** One post per gate and per new item (R3), printed in this session at end of turn; no file, no grammar. Contents in order: `references/stops-and-posts.md` §Status post, the `state.md` path last. `stage` follows `references/stages.md` §Run-level `stage`. Every turn ends by writing `state.md` and printing its path.
14. **CYCLE DONE, in this order.** (1) `pm` `release_record` line 1 terminal; (2) every `subtasks[]` entry `cleaned`; (3) `delivery-cleanup` `MODE=final` (no `SUBTASK`) once; without `cleanup-<run-id>-final.md` line 1 `CLEANUP DONE final`, post the `.tmp` path and its SPOT-CHECK block as a human step, advance nothing and re-run only on the owner's word (default, 29-30); (4) stage 8: dispatch the capture agent (`skills/delivery-run/references/briefs/capture-agent.md`) to draft the retro, the execution-log row, the session dump and the learnings into `RUN_HOME/capture/` (queued until the Hermes port is on, D19); write `RUN_HOME/retro.md` and the `RUN_HOME/execution-log.md` rows (one per unit, template Part B) from those drafts; dispatch a different agent as read-back (`briefs/read-back.md`) to check them against the run record, writing `capture/read-back.md` line 1 `READ-BACK: pass|<n> differences` (one fix and re-run, then the owner; 29-24); placeholder grep clean; (5) `TICKET-EVENT <key> done` for each ticket (D3), run `ticket-clerk` once more; (6) write `stage: done`, print `CYCLE DONE`, and the final post, led by the `release_record` line 1 and, on `ROLLED-BACK`, the rollback evidence path. Its human steps (plan-plane commit, profile restore, archive; the conductor never writes the profile): `references/stops-and-posts.md` §Final post.

## Red flags
| Thought | Do instead |
|---|---|
| "I'll peek at the sub-task bus to see progress." | Never read a bus. `state.md`, `substate.md`, inbox, outbox, escalations and record files only (C5, E7). |
| "The human said yes in chat; I'll write `H1.ok`." | The desk writes `gates/`; the conductor only reads file presence. |
| "H-e2e / H-pr is a formality, skip it." | Wait for the file or the read-back. A gate is never skipped, assumed or written. |
| "This lead outbox line is `pr-merge`; relay it." | Conductor-only verbs are never relayed: rename `.desk.refused` and post it. |
