# Resume: conductor resume, `REBIND`, applied-result scan, lead relaunch

Authority: card 1 (resume, missing-state stop; D8 29-9), INTERFACES 1.9.0 B1 (registry, re-claim, applied-result scan R4-J9, `.out` polling), B8 (`REBIND`), C5.1, C5.3, A.2 (AM-4 W2-5), A.3 (lock), A.4; adopted conventions A.8 (`RESUME` semantics, AM-6 (f)), B9 (GATE `<run-id>`, AM-6 (f)), C8 (`provenance.md`).

## Conductor resume (input `RUN_HOME`)

Run in this order; nothing is sent to the desk and no lead is launched before step 7. The applied-result scan (step 4) comes before every send, the registry re-send included (B1 "before any send").

1. **Step 0 and ORCHESTRATOR-CHECK** (`SKILL.md`). `RUN_HOME` is an existing directory under `$DELIVERY_ROOT` holding `state.md` (D2.2 row 1).
2. **Read `state.md`.** Missing (`INPUT-ERROR RUN_HOME path`) or unparsable (`INPUT-ERROR RUN_HOME format`): derive the rebuild from the run's own files (`RUN_HOME/*/substate.md`, `merge-*.md`, `cleanup-*.md`, `gates/`, `tickets.tsv`, `RUN_HOME/desk/*.out`, the dispatch plan), marking no step done that lacks its record, print it as the report and write nothing, then stop (card 1 stop). The run continues only on the owner's word.
3. **Version pins.** Compare `interfaces_version` with the live `INTERFACES.md` (`<version>@<sha256>`) and each `skill_versions` entry with the installed target hash. A mismatch means an amendment or a reinstall landed mid-run: stop and report (D7 change control; reviewed content must equal running content, design §6.5). Never rewrite a pin to make it match.
4. **Applied-result scan (R4-J9), before any send.** Scan `RUN_HOME/desk/*.out` for ids with `<subtask>` `run` of the conductor's own verbs whose result the record does not yet show, and apply each (local writes only):
   - `pr-merge` `DONE` with no `merge-<sha>.md` or no `merge_sha` in `state.md`, only the newest `pr-merge` `.out` per sub-task (`fields.subtask`) and only when its `expect_head` equals the current `substate.md` `head`, the sub-task is `pr-open`, and its request id time is later than any `reentered_utc` (29-25; a stale DONE of an earlier head is never applied): write `merge-<sha>.md`, set `merge_sha` and `state: merged`, then the `MERGED` inbox and any due `RELEASE` (`stages.md` stage 5b step 4).
   - `pr-approval-state` `DONE` with `h_pr` true and no pointer in `gates.H-pr`: append it.
   - A terminal `REJECTED` `.out` or a `.req.noreply` of an own request: re-post it as a human step; for `pr-merge` it stays the sub-task's 5b block marker (29-16), so no new `pr-merge` is minted for that `head`.
   - `jira-*` results belong to `ticket-clerk`, which applies its own on start (A.6); the conductor only re-reads the epic key from `tickets.tsv`.
5. **Own machine row.** Mint the new conductor session token (`launcher.md`), write its row under `machine/.lock` (the old row's dead pid is reaped to `.dead`), and update `machine_ledger_row`.
6. **Re-arm** the 1-minute relay tick (session crons do not survive the session). Until step 7 has `REGISTERED <run-id> | run | ok`, the tick sends, relays, renames and launches nothing and `ticket-clerk` does not run (tick step 0, 29-16), except the `run` claim and its re-send (29-27).
7. **Registry re-send (B1).** Send `REGISTER-SENDER <run-id> | run | <own sender-id>` first, then one line for every `subtasks[]` entry whose `lead_id` is set and not `-`. A repeated identical line is `ok`.
   - `run` answered `refused` (the run is claimed by the old conductor's sender id): post a human step asking the owner to type `REBIND <run-id> <sender-id>` in the desk session (regex `^REBIND ([a-z0-9-]+) ([^ ]+)$`, B8), with this session's sender id. Wait (default); send nothing else (the tick only reads). After the desk rebinds, re-send the `run` line (exempt from the send gate, 29-27) and, on its `ok`, every other line. A `REGISTER-SENDER` with no reply follows the one no-reply rule (`tick-relay.md` §4).
8. **Requests and carriers in flight.** Re-attach every own `RUN_HOME/desk/*.req` (never `.req.noreply`) that has no `.out` and that a record owns (a `pr-*` request of the 5b step in flight, or a `pm/outbox/*.sending-<id>` carrier): poll and resend the same id once per B1. A `.req` whose verb and fields match an un-renamed `pm/outbox/<seq>.conductor-request` is adopted by that carrier (rename it `.sending-<id>`), never minted again (29-16). Every `RUN_HOME/pm/outbox/*.conductor-request.sending-<id>` is re-sent with the same `<id>` (never re-minted) and renamed `.sent-<id>`; unrenamed `outbox/<id>.desk` and `outbox/register` files are handled by the next tick as usual.
9. **Inbox replay.** For each sub-task: an inbox `release` file whose effect `state.md` lacks -> set `state: released`, `released_utc`. Then re-derive every due `RELEASE` (`RELEASE pm` included), `MERGED` and `INVALIDATE` from `state.md` keyed on the current cycle (`reentered_utc`, `released_utc`, `launched_utc`, `merge_sha`) and write each one once (29-14, 29-25; `tick-relay.md` §Inbox writes). This covers a crash after `MERGED` and before the successor's `RELEASE`, and a back-edge written before its `INVALIDATE`.
10. **Dead lead state (card 1, C5.3).** For every sub-task that is `released`, `building`, `pr-open`, or `merged` and not yet `cleaned`: apply the `tick-relay.md` §7 test (29-13, 29-26): skip a sub-task whose current-session pid is live or whose `launched_utc` is under 10 minutes old; test only a `substate.lock` newer than `launched_utc`, and relaunch (below) when its owner pid fails `kill -0`; an older lock (the previous lead's) is left for the new lead to break and is no relaunch trigger; with no newer lock the sub-task gets the startup check, never a second launch under the same token.
11. **Continue** at `state.md` `stage` (`stages.md`), entering each stage by its re-entry predicate (29-17), then print the status post (every open item counts as new once):

| `stage` | Skip the stage skill when | Else |
|---|---|---|
| 1 | `repo_profile` set (or re-derived as `<profile path>@<sha>` from the profile file `delivery-intake` wrote) | re-invoke `delivery-intake` |
| 1 -> 2 | `gates/H0.ok` exists | wait for it (post) |
| 2 | `review-architecture.md` line 1 `ARCH: ready`, and when the live H1 file is `H1.changes`, the record is newer than its `utc=` (29-17) | re-invoke `delivery-architecture`, then record `h1_handled` |
| 2 -> 3 | live `H1.ok` recorded in `gates.H1`; an `H1.changes` whose name and `utc=` equal `h1_handled` is already handled | apply the H1 branch once |
| 2 -> 3, tickets | `gates.H1` set, `epic` filled and `tickets.tsv` present | run `ticket-clerk`, copy the epic key, append the `published` events not yet in `ticket-events.log` (29-17) |
| 3 | `plan-check.md` line 1 `PLAN-CHECK: clean`, no round-3 open finding (29-23), `subtasks[]` filled; after a post-merge re-entry also a `dispatch-plan.md` row for each new `st<N>` and `plan-check.md` newer than `pm/new-units.md` (29-29) | a `PLAN-CHECK: <n> findings`, a round-3 stop record in the plan's review section, or a dispatch-plan stop line (no `plan-check.md`): re-post the stop with its path and wait; re-invoke only on the owner's word (29-34). Else re-invoke `delivery-dispatch-plan` (with `NEW_UNITS` on a re-entry); fill `subtasks[]` |
| 4-7 | always continue on the tick | - |
| 8 | `capture/read-back.md` line 1 `READ-BACK: ok <path>` (D1.1, INTERFACES 1.8.0 AM-8 V16; 29-24) | re-run the capture step |
| `stopped` | `cleanup-<run-id>-final.md` line 1 `CLEANUP DONE final` | run `delivery-cleanup` `MODE=final` once, then report (29-30) |

A `stopped` sub-task (not the run-level `stage: stopped`) stays `stopped` at resume unless `RUN_HOME/gates/RESUME.<subtask>.<run-id>.ok` exists (A.8, B9); with it the sub-task returns to its pre-stop phase (the desk cleared `stop_reason`; INTERFACES 1.6.0 AM-6 (f)) and its lead is relaunched below.

## Lead relaunch (C5.3)

**Triggers:** reboot; `stop_reason: spawn-cap` read in `substate.md` (the old lead wrote it, removed its lifetime `substate.lock` and exited); a dead lead found at conductor resume; a dead lead found on the 1-minute tick (owner pid fails `kill -0` while `state` is `released|building|pr-open`, or `merged` and not yet `cleaned`); a `claude -p` lead's clean wait exit (28-CV47, owner answer O5, C8: no invocation live, `substate.lock` removed, `phase` and `stop_reason` unchanged), relaunched when the conductor writes the waking inbox file (`RELEASE`, `MERGED`) or the desk writes `ANSWER`, and on the next tick for a lane wait or `RELEASE: WAITING-HUMAN`; a clean wait exit is not a dead lead and does not count toward the one-relaunch rule (`tick-relay.md` §7).

| Backend | Action |
|---|---|
| `claude-p` | Wait until `RUN_HOME/<subtask>/substate.lock` is gone (the spawn-cap hand-over) or stale (dead owner pid; the new lead breaks it per A.3, the conductor never does). Run the `launcher.md` ledger check, then launch a fresh child with the same D2.2 row 6 inputs, a new `session` token, and the brief `resume <subtask>: re-read substate.md, inbox/ and gates/` on stdin |
| `agent-tool` | Ledger check, intent write, then a status-post line asking the owner to start a new session with the full `delivery-run` call (D2.2 row 6 inputs with the new `SESSION`) followed by the brief (C5.3; `launcher.md` §Which backend) |

- `subtasks[].state` is unchanged by a relaunch. The new lead clears `stop_reason: spawn-cap` at its resume (A.3, AM-4 W2-5) and registers again: each lead start renames earlier `register*` files and writes a fresh `outbox/register`, which the tick consumes (`lead_id`, `session` updated; the desk replaces the sub-task's sender id, B1).
- The new lead is a new session, so its spawn count starts at 0 (A.3).
- **Launch intent first (29-13).** After the fail-closed checks and before exec the conductor writes the new `session` (`-l<n>`, `n` = the stored count + 1, replacing the old token, which no longer counts in the ledger), `launched_utc` and `relaunch_phase` (the current `phase`) to `state.md` (29-26). A lead whose current-session pid is live is not dead; skip it.
- A lead that dies again with `phase` still equal to `relaunch_phase` is reported to the owner with the sub-task, both session tokens, `homes/<session>/lead.log` and `substate.md` paths, and not relaunched a third time (the conductor's reading of "never a third attempt", with stop-and-report from card 1; C8 29-6, owner item O-2 lead default); the `spawn-cap` trigger counts the same way, so a missing lock does not re-trigger every tick.
- A `merged` sub-task not yet `cleaned` is relaunched only to run `delivery-cleanup` `MODE=subtask` (its lead still owes it; owner item O-2 lead default, C8 29-6).
- A second `pm` lead that finds a fresh `substate.lock` refuses to start and writes `STOP stale-session` to `RUN_HOME/pm/outbox/stop-<utc>.md`; the conductor records `stop_reason: stale-session` in `state.md` `subtasks[]` and maps `pm` to `stopped` (INTERFACES 1.9.0 AM-9 G1/6; O-1 default): post it as a human step; no relaunch while the old lock is fresh; `RESUME.pm` is the exit.
- Not relaunched: a `pm` with `postmerge: FAIL`, a `POSTMERGE: STOP` record with no later `RESUME.pm.<run-id>.ok` gate (AM-7 E47; `tick-relay.md`), a `stop_reason: human` (`stopped`, 29-31) or a terminal `release_record` (29-19).
- `wave-execution` resumes from its checkpoint because `session_id` is unchanged; the lead's own C5.3 steps (slot rows, catalog audit, lease reclaim, pm2 check) are `delivery-run`'s, never the conductor's.
