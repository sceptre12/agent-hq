**Namespacing (M12, §4):** every pm2 app, bus `data_dir`, temp dir and worktree name carries `<run-id>-<subtask>`.
**Multi-repo epic (§5.0):** the primary repo governs; other repo profiles are linked from it (`linked_profiles[]`, A.2.2). The human names it at stage 1 as the `PRIMARY_REPO` input of `delivery-pipeline` (part D2.2 row 1), the conductor records it as `state.md` `primary_repo` before it creates `plans_dir`, and `architecture.md` §3 restates it and names the other repos (`DEFAULT (integrator)`, r3b V3-4).
**Atomic writes (`DEFAULT (integrator)`):** `state.md`, `substate.md`, gate files, slot rows, `bus.endpoint` and every `.out` are written to a temp file in the same directory and `mv`d into place. A file written by several agents of one kind is named `<agent-id>-<purpose>-<n>.md`. ### A.2.1 Human gate files and pointers (M30, §5.0, §0.1)

**AM-5 (26, decided by the desk loop):** every gate-file name carries the run id as `<gate>.<run-id>.ok` (so one desk session serving several runs cannot confuse them): `H0.<run-id>.ok`, `H1.<run-id>.ok|.changes|.reject`, `H-e2e.<subtask>.<run-id>.ok`, `H-prod.<step_id>.<run-id>.ok`, `grant.<subtask>.<n>.<run-id>.ok`, and the new `H-destructive.<row-id>.<run-id>.ok` (AM-5 21: a human grant for a destructive post-merge test row, `RUN_HOME/gates/`; `post-merge-verify` refuses the row without it). The rows below read with that suffix.

The desk writes a gate file after the human types a `GATE` line in the desk session (grammar and gate x verdict matrix in part B8). `substate.md` is the lead-to-conductor transport for `PREPR`, `INTEGRATED`, `CI` and `POSTMERGE` results (`DEFAULT (integrator)`): producers `pre-pr-gate`, `delivery-run` (Integrator step), `ci-fix-loop`, `post-merge-verify`, each through the lead; consumer the conductor (`delivery-pipeline`) on its tick. The lead sends `pr-create` only after `prepr: PASS` for `head`; the conductor sends `pr-merge` only after it reads `pr` set, `ci: GREEN <sha>` and `prepr: PASS` with `head` = `<sha>` and `review_record` = `record-<sha>.md` (B5 re-derives the review record on the landing head); when `ci-fix-loop` moved the head the lead re-runs `pre-pr-gate` with `HEAD=<sha>` first. A later push to an open PR needs the `GATE-PASS` record for its head plus either `RUN_HOME/ci/<pr>.md` naming the head or `PREPR: PASS` for it (AM-4 24-Q2, W2-7) (part B4 requester column).

**Lock (§4; lifetime lock, `DEFAULT (integrator)`):** the lead runs `mkdir RUN_HOME/<subtask>/substate.lock` at start and holds it for its whole lifetime (header writes need no second lock). It writes `owner` (`<pid> <ISO UTC>`, regex `^[0-9]+ [0-9TZ:-]+$`) to a temp file in the lock directory and `mv`s it to `owner`. The lock is stale when the `owner` pid fails `kill -0`, or when `owner` is missing or unparsable and the directory is older than 120 s; a stale lock is broken and the break is logged in `substate.md` (`lock_breaks: [<utc>]`). **Break (`DEFAULT (integrator)`, all four `mkdir` locks: `substate.lock`, `machine/.lock`, `catalog.lock`, `desk/.lock`):** `mv <lock> <lock>.broken-<pid>-<yyyymmddThhmmssZ>` (an atomic rename; only one breaker's `mv` succeeds), then reads `owner` inside the renamed directory: if it is not the `<pid> <utc>` it tested stale (another breaker's fresh lock was moved), it renames the directory back to `<lock>` (a plain rename, never `mv` into an existing directory) and starts over (row R4-J10); else `mkdir <lock>`; a breaker whose `mv` or `mkdir` fails starts over from the stale test; a waiter retries every 1 s and gives up after 60 s (`catalog.sh` and `desk-req.sh` exit 4, INTERFACES.md script table); the renamed directory is removed after the new lock is held. Hand-over on the spawn-cap path: the old lead writes `stop_reason: spawn-cap`, removes its lock and exits; the new lead refuses to start while the lock exists and is not stale (part C5.3). The new lead is a new session, so its per-session spawn count starts at 0.

The new lead clears `stop_reason: spawn-cap` at resume; a lead clears `invalidate` when it consumes the fresh `RELEASE` (AM-4 W2-5).

**`bus.endpoint` (§5.0, §3.0, B1):** key=value lines `port=`, `data_dir=`, `pm2_app=`, `pid=`, `session_id=`, `topic=`; written atomically (temp file plus `mv`) by `delivery-run` after it starts the bus and before any dispatch. `session_id=` must equal the bundle `session_id` and `topic=` the bundle `output_topic` (`DEFAULT (integrator)`: the bundle is the source of truth; a mismatch is a stop row). `data_dir=` is absolute; `wave-execution` reads `port` from `$data_dir/port` (ADR 0054 A9, part C1.1). `session_id` and `topic` are added because §3.0 says the done token is posted "on the topic named in `bus.endpoint`" (design errata: §5.0 lists four fields).

## A.4 Slot row file (design §5.0, §4, B5, A3, D25)

One file per dispatched agent: `RUN_HOME/<subtask>/slots/<agent-id>.row`, written by the lead **before** the dispatch for every agent the lead dispatches itself, except reserved-seat agents (shepherd, ci, review seats; the clerk has no per-sub-task row, it runs only in the conductor session, AM-8 V8), which are counted by A.3 `reserved` and get no row; the gate runner and every other agent get a row (`DEFAULT (integrator)`). The `wave-execution` controller task gets a row (`persona` `wave-controller`, `unit` `-`, `budget_min` the sum of the invocation's work_item `budget_min`), written before its Agent call; `max_concurrent` is computed after it; one live invocation per sub-task (AM-4 W2-2). Agents dispatched by `wave-execution` (worker, gate and fix agents) count toward the invocation's `max_concurrent` (owner 2026-10-26, ADR 0054 Q3, `architecture/delivery-workflow-sources/owner-decisions.md:74`; `decisions/0054-adr-0023-amendment-delivery-workflow.md:55-61`), so the controller itself keeps them within the free slots the lead passed (part C1.1) and no reservation is needed. ### A.5.2 Port claims (amendment AM-1; owner 2026-10-26, PORT GUARD)

The single statement of the port guard. **Scope:** every port a run binds: e2e lanes, dev servers, the sub-task bus and `pr-review`'s per-review bus. **Order before launch:** (1) `tools/port-check.sh --claim <port> <bind> <container_port> <service> <project> claimed <source> <note>` (through the `port-claim` skill), with `project` = `<run-id>` and `source` = `<run-id>-<subtask>` (`DEFAULT (integrator)`); (2) `catalog.sh register port <port> ...` (`planned`); (3) the launch; (4) `catalog.sh start` (`live`). The candidate port is fixed before any check by the dispatch-plan port table: `<base> + 20·k` (`st<N>` bus `k = 2N`, review bus `k = 2N + 1`, lane binds by consecutive bind index; fixed app ports keep their app port), so the one +10 retry of any candidate lands on an odd ten that no candidate uses; the plan checks that all candidates and all candidates + 10, across both bases and the fixed app ports, are pairwise distinct and at most 65535 (AM-4 W2-3). A bus server is started with `PORT_RANGE_START=<port> PORT_RANGE_END=<port>` and its `$DATA_DIR/port` must equal the claim. The +10 offset is applied exactly once after a refusal, as the single retry candidate, and never a second time (AM-3, OQ-2; this overrides the AM-2 row 6 / PC-4 "never applied" default). **Collision:** exit 1 (taken) or 2 (registry and `lsof` disagree) refuses the launch; the launcher **never auto-picks** another port; on the first refusal it makes **exactly one retry at candidate + 10**, itself claimed with `port-check.sh --claim` before any bind (the tool still never auto-picks), and a second refusal stops the line and is reported to its lead (a lane maps to C2 reason `lane-unavailable`); exit 3 (registry unusable) is stop-the-line (for a lead-owned claim, written `stop_reason: port-refused`; no retry after exit 3; AM-4 W2-1) (AM-3, owner OQ-2, `architecture/delivery-workflow-sources/owner-decisions.md` "Plan-check owner questions"; applies in delivery runs and to standalone `pr-review`). **Release:** cleanup only, per the `port` row of A.5.1. **Hook:** the PreToolUse(Bash) hook `tools/hooks/port-precheck.sh` checks launches made outside this path against `tools/app-ports.tsv` and `lsof` and asks the human on a live listener; it is advisory and always exits 0. **Move and P0:** the move installs the hook from `config/settings.json` and fills `tools/ports.tsv` and `tools/app-ports.tsv` for the work machine; P0 runs a positive control (a listener on an `app-ports.tsv` port plus that row's launch command must return `permissionDecision: "ask"`; silence fails P0). Lands as agent-hq PR #9 (branch `wt/port-guard`).
