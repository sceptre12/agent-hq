# post-merge-verify

## Trigger
Use when: the `pm` lead (inside `delivery-run` mode `post-merge`, no seed, no waves, no bus; INTERFACES part-a A.2 "Stages 6-7 host") holds `PM_SHA`, the `merge_sha` of the last sub-task merge, and must prove main against `test-plan.md`. Output feeds the conductor (`PASS` maps to Verified; `FAIL` re-enters `delivery-dispatch-plan` with `NEW_UNITS`) and `release-track` (reads the record as `POSTMERGE_RECORD`).

## Inputs and Step 0
Inputs (`NAME=value` in the arguments, part-d D2.2 row 12): `RUN_HOME` (path; its last segment is `<run-id>`), `PM_SHA` (sha), `PLANS_DIR` (path; holds `test-plan.md` and `dispatch-plan.md`), `WORKTREE_BASE` (profile `worktree_base`; INTERFACES 1.8.0 AM-8 V4). `DELIVERY_ROOT` is the environment variable only. Arriving inline in the lead's call (the lead is the A.2.2 reader): `REPO_PROFILE` (`<abs path>@<sha>`, the lead's own `delivery-run` input, D2.2 row 6). The repo path is `primary_repo`, read from `RUN_HOME/state.md` (the only `state.md` field this skill reads, A.2).

Step 0, before anything else (part-d D1): validate each item below. Print one line per failing field, then stop (no retry, no prompt): `INPUT-ERROR <field> <reason>`, reason in `missing|enum|path|unset|format|sha` (part-d D1, INTERFACES 1.9.0).
- `DELIVERY_ROOT` set (`unset`); `RUN_HOME` an existing absolute directory under it (`path`); `PM_SHA` matches `^[0-9a-f]{40}$` (`format`); `PLANS_DIR` holds `test-plan.md` with a post-merge section, and `dispatch-plan.md` when any row names a lane (Step 4 reads its port table) (`path`).
- `WORKTREE_BASE` present (`missing`) and matching `^/[^[:space:]]+$` (`format`); `REPO_PROFILE` present and of the form `<abs path>@<40-hex>` (`format`) whose `git hash-object` equals the sha (`sha` on a mismatch; A.2 `repo_profile` rule); `primary_repo` an existing directory (`INPUT-ERROR primary_repo path`).
- Profile keys, read from the profile blob at the pinned sha (`git -C <primary_repo> cat-file blob <sha>`, A.2 `repo_profile`), never from the working file. A missing key is `INPUT-ERROR <key> missing` (A.2.2); a `FILL_IN_BEFORE_DISPATCH` value is refused (sentinel convention, `skills/delivery-intake/references/templates/repo-profile.md` §2) and reported as `format`. Always `merge_pipeline.stages[]`, `node.prefix_cmd`, `secrets.pattern_file`, `durations.ci_round_min`, `durations.unit_median_min`, `durations.pr_review_min` (A.2.2; the last two are slot-row budgets), and `commands.install` (design part-04 §5.8; template line 30); `commands.pack` (template line 36) and `repo.consumer_repos[]` (template line 28) only when the plan has consumer-simulation rows; `e2e.harness` (template line 87; enum `nlta|none`, part-d D2.1) only when it has e2e rows (`enum` unless `nlta`). This skill as an A.2.2 reader of `commands.install`, `commands.pack` and `repo.consumer_repos[]`, and `REPO_PROFILE` in D2.2 row 12, are INTERFACES 1.5.0 (AM-5 21: part-d D8, A.2.2 readers). Points marked "lead decision, not carried by 1.5.0" below are item-21 lead decisions that no amendment carries.
Export `RUN_HOME` and `WORKTREE_BASE` for every `catalog.sh` call (INTERFACES script table: with `WORKTREE_BASE` unset only `RUN_HOME` is a legal root, so the worktree handle is rejected exit 2).

## Steps
1. **Read the plan.** Read the `PLANS_DIR/test-plan.md` post-merge section (columns per design part-04 §5.4). Per row take: id, what it proves, command, lane, expected, evidence owner, cold-run, order or seed, `gating` or `informational`, failure policy. Also take the test-management reporting row and the explicitly-not-tested list. Consumer-simulation rows (§C, each with its `class` column, INTERFACES 1.6.0 AM-6 B-9c) form a fourth set: Step 7 runs them and the verdict agent writes their `.line` (Step 10). Every profile `merge_pipeline.stages[]` name must be covered by one post-merge row (owner OQ-A recommendation, lead decision); an uncovered stage is a stop condition before any run. Sort the §B rows into three more disjoint sets, each with one `.line` writer:
   - **Hand-test rows:** `evidence owner` is `human` (template `test-plan.md` §B: "same columns, `command` is the written manual procedure, `evidence owner` is `human`"). Step 8 only; never given to a runner, a lane lease, a port or a slot.
   - **Stage-covered rows:** the command is the `ci-status-main` read of a merge-pipeline stage. Step 9 only; no runner runs them.
   - **Runner rows:** every other row. Steps 3-6. An e2e row among them is one whose command names a `.feature` path listed in the plan's §A3 batched `.feature` list (design §3.6 steps 3 and 8: stage 6 re-runs the e2e rows; the target comes from the `.feature` path). A §A3 `.feature` path that no §B row names, with `e2e.harness` `nlta`, is a stop condition (ambiguous e2e coverage; open author question to item 27, template).
   A row id outside `[A-Za-z0-9.-]+` (part-d D2.2 row 12) is a stop condition: report the bad row id to the `pm` lead, never rename the row. Quote each row's failure-policy text verbatim and apply it literally; an empty or unclear policy means no retry and the row fails.
2. **Add the worktree.** Add a detached worktree of main at `PM_SHA`, path `<WORKTREE_BASE>/<run-id>-pm` (A.6 R4-J17). The `pm` lead normally created it as its first step (INTERFACES 1.6.0 AM-6 (b)), so this step finds it. If the path already exists: reuse it only when `git -C <path> rev-parse HEAD` equals `PM_SHA`, `git status --porcelain` is empty and your catalog row for it is `live` (resume); otherwise stop and report to the `pm` lead (never delete, never pick another path). New: `catalog.sh register worktree '<path>#<primary_repo>@main' - run post-merge-verify pm <agent_id>`, then `git -C <primary_repo> worktree add --detach <path> <PM_SHA>`, then `catalog.sh start worktree '<path>#<primary_repo>@main'`. If `worktree add` fails, run `catalog.sh fail worktree '<path>#<primary_repo>@main'` (A.5 `fail`; no `planned` row is left) and stop. Verify HEAD equals `PM_SHA`. In the worktree run the profile `node.prefix_cmd`, then the profile `commands.install` (frozen-lockfile, scripts ignored; a lockfile restore, never a new dependency).
3. **Lane leases, before any port or launch.** The lead, for each distinct lane name among the runner rows (skip lane `-` or empty), takes the lease and holds it for that lane's runner: `catalog.sh register lane-lease lane/<name> - run post-merge-verify pm <agent_id>` (A.5: `register` writes `live` directly). Exit 3 means the latest row for that handle is `planned` or `live` (held): claim no port and launch nothing for that lane; stop and report the lane name and holder row to the `pm` lead; never wait, steal or release another holder's lease. C2 `lane-unavailable` is defined only for a refused port pair (A.5.2), so a held lease is stop reason `lane-held` (OQ-F). Rows sharing a lane run serially in the plan's order or seed; lanes run in parallel, one runner each, only with a free slot (A.4: `max_concurrent = 30 - live_rows - sum(A.3 reserved)` above 0). Before each dispatch the lead writes the A.4 slot row `RUN_HOME/pm/slots/<agent-id>.row` with all 9 fields: `persona` `lane-runner`, `unit` `-`, `tier` `mechanical` for an e2e lane runner (design part-03 §3.2 "never debugs"; spec 21 "execute runners" is errata, lead decision, not carried by 1.5.0) and `execute` for any other runner, `budget_min` the profile `durations.unit_median_min`. The verdict agent frees runner rows (Step 10).
4. **Ports before bind (A.5.2, owner OQ-2), leased lanes only.** For each leased lane, take every candidate port from the `PLANS_DIR/dispatch-plan.md` port table rows with role `lane/<name>` (lane leases are run-wide, so the `pm` lead reuses the lane's candidate). A bind with no such row has no candidate: stop and report to the `pm` lead; never pick one. A runner row with lane `-` or empty whose command starts a server or names a port to bind is never run: the port table keys candidates by `lane/<name>`, so it has no candidate and no lease, yet A.5.2 covers "every port a run binds"; stop and report it to the `pm` lead (open author question: the plan gives such a row a lane). Per candidate, in order:
   1. Claim through `port-claim`: `tools/port-check.sh --claim <port> <bind> <container_port> <service> <run-id> claimed <run-id>-pm <note>`.
   2. Exit 1 or 2 (first refusal): do not launch; make exactly one retry at candidate + 10, itself claimed with the same `--claim` call before any bind. Never a second +10, never another number.
   3. Retry refused too: stop the line and report to the `pm` lead with C2 reason `lane-unavailable`. Exit 3 at either claim: stop the line.
   4. Exit 0: `catalog.sh register port <claimed-port> - run post-merge-verify pm <agent_id>`; register the server (`references/ports-and-servers.md`); launch; `catalog.sh start port <claimed-port>`. A failed launch: `catalog.sh fail port <claimed-port>` and `catalog.sh fail pm2-app <name>`, then stop and report.
   Release of ports and servers is `delivery-cleanup`'s (A.5.1, A.5.2 "Release: cleanup only"), not yours.
5. **Run rows, cold.** Each runner runs only runner rows (never a hand-test or stage-covered row): it executes the row's command in the worktree (`references/row-execution.md`). A result the tool reports as served from cache is not a run: the row is `FAIL` with evidence key `cache-served`. Write the output tail and exit code to `RUN_HOME/pm/evidence/<row-id>.log` and the row's staged evidence line to `RUN_HOME/pm/evidence/<row-id>.line` (format `references/record-format.md`; the runner is the single writer of the `.line` of the rows it runs).
6. **E2E rows.** An e2e row takes Step 5's evidence rules and runs through `nl-run-e2e` in the worktree. The Test-adequacy seat (dispatched in Step 10) reviews every auto-healed diff and is the single writer of `RUN_HOME/pm/evidence/<row-id>.heal-review` (one `<diff-path> accept|reject` line per diff: a per-diff review decision, not a verdict vocabulary; the row result stays `PASS`/`FAIL`, lead decision, not carried by 1.5.0); a healed pass counts only when every diff is `accept` there; never accept blind. `SOURCE_BUG` is a stop condition (below); `ENV_BUG` fails the row with reason `env-bug`. Details: `references/e2e-rows.md`.
7. **Consumer simulation.** Run the profile `commands.pack` once, serially, in the worktree; one runner (slot row as Step 3, tier `execute`) runs each consumer-simulation row against that one artifact and writes only its `.log`; the verdict agent writes the row's `.line` (Step 10). Details: `references/consumer-sim.md`.
8. **Hand-test rows** (evidence owner `human`, Step 1). An agent never executes a hand-test row (card 12; design part-04 §5.4; D17 "testing plan covers by hand post-merge"). The lead (single writer) stages one `human` line per row in `RUN_HOME/pm/evidence/<row-id>.line`. Hand-test rows are `informational` only (OQ-C recommendation; `delivery-architecture` refuses a gating one); a `gating` hand-test row is a stop condition before Step 10.
9. **Merge pipeline.** Request desk `ci-status-main` `{repo: <primary_repo>, merge_sha: <PM_SHA>}` (never a PR head) with `desk-req.sh <run-id> pm ci-status-main <fields-json-file>`, send it per the lead's backend, poll the `.out` and handle `REJECTED` and no-reply exactly as `references/merge-pipeline.md` says (part-b B1, B2.1, B4; part-c C5.2). The lead (single writer) stages the stage states in `RUN_HOME/pm/evidence/ci-status-main.stages`, one line per profile `merge_pipeline.stages[]` name, and writes the `.line` of each stage-covered row. A stage `pending` or absent from the `.out` at the first read gets one `durations.ci_round_min` wait and one re-request; still `pending` or absent after it is a stop condition (OQ-G). A `skipped` stage is not `success` (OQ-H): it fails a covered row. A `failure` or `cancelled` stage fails its covering row.
10. **Verdict (verify tier), after every runner has finished.**
   1. If any e2e `.line` names a healed diff, the lead writes a slot row (`persona` `review-seat`, `unit` `-`, `tier` `verify`, `budget_min` `durations.pr_review_min`) and dispatches the Test-adequacy seat (design part-03 §3.6 steps 6 and 8). The `pm` lead hosts no review rung, so this seat is not in A.3 `reserved` and takes a slot like any agent (lead decision, not carried by 1.5.0). It writes `<row-id>.heal-review` (`references/e2e-rows.md`).
   2. Then the lead writes the verdict agent's slot row (`persona` `validator`, `unit` `-`, `tier` `verify`, `budget_min` `durations.pr_review_min`) and dispatches it. The verdict agent reads the staged `RUN_HOME/pm/evidence/*.line`, `*.heal-review`, `ci-status-main.stages` and any unconsumed desk `VERDICT pm` inbox file (AM-7) and the `.log` files they name, never the runners' summaries. It writes the `.line` of each consumer-simulation row from its `.log` and renames no slot row; on its report the lead renames finished runner and seat rows `.freed` (C7; AM-8 V10).
   3. It returns its verdict as the C5.1 inbox message `RUN_HOME/pm/inbox/<seq>-<yyyymmddThhmmssZ>-verdict.md` to the lead (`<seq>` the next free one; INTERFACES 1.6.0 AM-6 (a): the verdict is an inbox message from the verdict agent; the desk's only `VERDICT` line is the human-decision one, 1.7.0 AM-7 touch-up 7, B8, C8). Line 1 is the record's line 1 (`POSTMERGE: PASS` or `POSTMERGE: FAIL <ids>`), then one `<row-id> PASS|FAIL` line per row. The lead waits for that file at most the verdict row's `budget_min`; past it, `TaskStop` the agent and stop (`verdict-timeout`). Otherwise it frees the verdict agent's row.
   PASS only if every `gating` row passed. `informational` failures are recorded and never change the token. No weighted score.
11. **Write the record.** `RUN_HOME/postmerge-<PM_SHA>.md`: line 1 `POSTMERGE: PASS` or `POSTMERGE: FAIL <id>,<id>` (failed gating row ids; regex `^POSTMERGE: (PASS|FAIL)( [A-Za-z0-9.,-]+)?$`), then the body per `references/record-format.md`: one line per row id (gating, informational, consumer, hand-test as `human`), the merge-pipeline stages, the reporting row as `release-track`'s, and the explicitly-not-tested list copied from the plan. Test-management reporting is not this skill's step: `release-track` writes the `test-report-push` payload and requests the verb.
12. **New units on FAIL.** Write `RUN_HOME/pm/new-units.md`, one line per failed gating row: `<row-id> <one line>` (regex `^[A-Za-z0-9.-]+ .+$`; each id a plan row id). Do not edit code, open a PR, or retry a gating row beyond its failure-policy text.
13. **Report through `substate.md` (A.3, PASS and FAIL alike).** The lead (sole writer) sets `pm_sha: <PM_SHA>`, `postmerge_record: <abs path of postmerge-<PM_SHA>.md>` and `postmerge: PASS|FAIL` (the line 1 word); the conductor reads them on its tick.
14. **Release (also on a stop).** On a stop, `TaskStop` every agent still running, run the orphan sweep (part-c C7 "After every TaskStop"), re-read the staged `*.line` files and the `verdict` inbox file, then rename every remaining `RUN_HOME/pm/slots/*.row` to `.freed` (A.4, part-c C5.3 order). `catalog.sh release lane-lease lane/<name>` for each lane-lease the lead still holds, after that lane's last row (A.5.1 `lane-lease` row: "write a `released` row"). Leave `worktree`, `port`, `process`, `pm2-app` and `tmpdir` rows: `delivery-cleanup` applies the A.5.1 cleanup column, and the `pm` lead runs it in mode `subtask` for `pm` once `release-<pm_sha>.md` is terminal (part-c C5.1), after `release-track` has run in the same `pm` lead (A.2 stages 6-7 host). Run `catalog.sh list --live --subtask pm` and report every row you still hold.

**Stop conditions.** Stop: write `RUN_HOME/postmerge-<PM_SHA>.md` holding the single line `POSTMERGE: STOP <reason>` (regex `^POSTMERGE: STOP [a-z0-9-]+$`; part-d D1.1 as amended by D8, AM-5 21; reasons in `references/record-format.md`), no `new-units.md`, no `substate.md` `postmerge` value; report the reason to the `pm` lead, which writes `stop_reason: human` (the conductor reads it beside this record as that row, part-a A.2, AM-5 29-31); run Step 14 (lane-leases released, other rows stay for `delivery-cleanup`). The conditions:
- a product decision is needed to judge a row (`product-decision`; the conductor posts it to the owner, who answers at the desk; the desk writes the answer to `RUN_HOME/pm/inbox/` as a `verdict` message, line 1 `VERDICT pm <row-id> <text>`; the `pm` lead re-runs this skill for the same `PM_SHA`, and the verdict agent takes that line as the row's decision and the lead renames the file `.consumed`; INTERFACES 1.7.0 AM-7 touch-up 7, E47);
- a destructive row with no grant file `RUN_HOME/gates/H-destructive.<row-id>.<run-id>.ok` (desk-written on `GATE <run-id> H-destructive.<row-id> ok <text>`, part-a A.2.1, part-b B9, AM-5 21); the row is never run;
- `SOURCE_BUG` from an e2e row: escalate to the human; the report carries C2 reason `source-bug` (D2.2 note);
- a held lane lease (Step 3); a port claim refused twice (`lane-unavailable`) or `port-check.sh` exit 3; a lane bind with no port-table candidate or a `FILL_IN_BEFORE_DISPATCH` candidate; a lane-less row that binds a port (Step 4); a failed worktree add or server launch (`catalog.sh fail` first);
- a §A3 `.feature` path with no §B row; a plan row id outside `[A-Za-z0-9.-]+`; a `merge_pipeline.stages[]` name no row covers (Step 1);
- a stale or dirty existing worktree path;
- a `gating` hand-test row (Step 8);
- a consumer tmpdir that cannot be created, or a consumer row needing a dependency the lockfile does not hold (`references/consumer-sim.md`);
- on `ci-status-main` (`references/merge-pipeline.md`): `desk-req.sh` exit 2 or 4; `register.consumed` absent or `register.refused`; any `REJECTED`, terminal or curable; no-reply (no-reply and `sender` also write the B1 escalation, its `<unit>` the desk `<id>`, OQ-I); a stage still `pending` or absent past its bound.

## Red flags
| Rationalization | Do instead |
|---|---|
| "The cache is warm, a cached pass is the same" | Cold run only; a cache-served result is not a run. |
| "The heal diff looks fine, accept it" | The Test-adequacy seat reviews it; never accept blind. `SOURCE_BUG` stops the run and goes to the human. |
| "The flaky gating row passed on rerun, call it PASS" | Retry only as the row's failure-policy text says; otherwise it failed. |
| "The informational row failed, so FAIL" | Informational failures are recorded, never fail the token. |
| "That port is taken, use the next free one" | Refuse the launch; exactly one claimed retry at candidate + 10; a second refusal stops the line (`lane-unavailable`). |
| "The +10 retry failed, try +20" | Never a second retry; stop the line and report to the `pm` lead. |
| "No port-table row for this server, pick one" | No candidate means stop and report; never pick. |
| "The lane lease is held, wait for it" | Stop and report the lane to the `pm` lead now; never wait, never steal. |
| "Keep polling, the pipeline will finish" | One `durations.ci_round_min` wait; still `pending` stops and reports. |
| "Hand-test row is quick, run it" | It is the human's; list it as `human`. |
| "A failing row is a small fix, patch main" | A FAIL never edits code or opens a PR; write `new-units.md`. |
| "Report results to the test tool now" | `release-track` owns the report; record the evidence line only. |
| "Use the PR head sha for the pipeline" | `ci-status-main` takes `merge_sha` = `PM_SHA`. |
| "The runner says it passed" | The verify-tier agent decides from the staged evidence files. |

## Exit criteria
- [ ] Step 0 passed, or printed one `INPUT-ERROR` line per failing field and stopped.
- [ ] Every `catalog.sh` call ran with `RUN_HOME` and `WORKTREE_BASE` exported; worktree HEAD equals `PM_SHA`; no `planned` row of yours remains.
- [ ] Every lane lease was taken before its ports; every port bound (lane or not) had an exit-0 claim first, and no lane-less row bound a port; at most one +10 retry per candidate; every long-lived server you launched has a `pm2-app` row, and every listener a row's own command left behind has a `process` row; a failed add or launch has a `failed` row.
- [ ] No runner ran a hand-test (`evidence owner` `human`) or stage-covered row; each `.line` has one writer (runner for runner rows, lead for stage-covered and hand-test rows, verdict agent for consumer-simulation rows).
- [ ] On a stop condition: the record is the one line `POSTMERGE: STOP <reason>`, no `new-units.md`, reason reported to the `pm` lead.
- [ ] Every runner, seat and verdict agent had a 9-field A.4 slot row (persona, tier, budget) before dispatch; the lead renamed each `.freed` (AM-8 V10).
- [ ] Each consumer-simulation `.line` was written by the verdict agent; the verdict arrived as the `RUN_HOME/pm/inbox/` `verdict` message within its budget.
- [ ] Otherwise `postmerge-<PM_SHA>.md` line 1 matches the token regex; one line per post-merge row id; hand-test rows are `human`.
- [ ] Verdict is PASS only if every gating row passed, decided by the verify tier from the staged evidence.
- [ ] On FAIL, `pm/new-units.md` has one `<row-id> <one line>` per failed gating row, each id in the plan.
- [ ] `ci-status-main` was requested with `merge_sha` = `PM_SHA`, `repo` = `primary_repo`.
- [ ] No code edited, no PR opened, no promotion or deploy, no destructive row run.
- [ ] Lane-leases released (on a stop too); `substate.md` `pm_sha`, `postmerge_record` and `postmerge` set on PASS and on FAIL.
