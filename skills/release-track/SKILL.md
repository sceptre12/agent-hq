# release-track

Agents run staging and polling; humans run production; agents prepare the commands and track (D15). Two Zephyr products are involved and must not be confused:
- **Zephyr Cloud** (the deployment platform): the only access is this skill's own read-only leg through the MCP `execute` tool behind a hook (`references/zephyr-leg.md`, `references/hook-wiring.md`). No desk verb exists for it (B4 "Not verbs").
- **Zephyr Scale** (test management): test results go only through the conductor-only verb `test-report-push` (B4 `tool: zephyr`, Step 7). This skill never calls Zephyr Scale itself.

## Trigger
Use when: the `pm` lead has `post-merge-verify` passing for `PM_SHA` and the run has a `release-plan.md` v0. Do not use for a sub-task build (that is `delivery-run` mode `build`) or to run a production step.

## Inputs (Step 0)
`RUN_HOME` (path), `PM_SHA` (sha), `PLANS_DIR` (path; holds `release-plan.md` v0), `POSTMERGE_RECORD` (path), `REPO_PROFILE` (`<abs path>@<sha>`; reads `zephyr.read_ops`, `zephyr.execute_tool`, `release_tags.used|pattern|approval`), `STAKES` (`reversible|one-way`), `CONTENTION` (`none|contested`), `NOVELTY` (`known|novel`) (D2.1 enums, for the plan v1 review, Step 3; they reach the `pm` lead in its launch prompt from lines 2-4 of `PLANS_DIR/review-architecture.md`, written by `delivery-architecture`; absent, the conductor launches no `pm` lead; INTERFACES 1.10.0 C8 29-28, D8 row 3). `DELIVERY_ROOT` is the environment variable; unset, Step 0 prints `INPUT-ERROR DELIVERY_ROOT unset` and stops (A.1). `<run-id>` below is the basename of `RUN_HOME` (A.1).

## Steps
0. Validate inputs (part D1). Print one `INPUT-ERROR <NAME> <reason>` line per failing field (`missing|enum|path|unset|format`), then stop; never ask. A missing `zephyr.read_ops` or `zephyr.execute_tool` key is `INPUT-ERROR <key> missing` (A.2.2). A value still `FILL_IN_BEFORE_DISPATCH` is not an error: it means no `execute` call at all this run (Step 8). A missing `release_tags.*` entry is not an error either: send no `tag-push` (the desk would answer `REJECTED policy`, N11) and hand the tag step to the human. Check `POSTMERGE_RECORD` line 1 is exactly `POSTMERGE: PASS` (D1.1); if not, stop. Read `release-<sha>.md` if it exists: a terminal line 1 (`LIVE`, `ROLLED-BACK`) means done, report and stop; `WAITING-HUMAN` means resume: for each waiting step check its gate file (`RUN_HOME/gates/H-prod.<step_id>.<run-id>.ok`) or the human's report; present means continue that step at Step 7 or 8; absent means keep waiting and rewrite nothing.
1. Diff `PLANS_DIR/release-plan.md` v0 against what merged: the commits at `PM_SHA`, the sub-task merge shas, `POSTMERGE_RECORD`. List steps the merge made unnecessary, missing, or reordered. Keep every `step_id` of the v0 step table unchanged. Where the profile's `merge_reach` says the merge pipeline already reached production storage (on <pilot-app> the production S3 backup, under the human PR approval, R2-5), record that as done by the merge, not as a step to run; live production remains the human promotion. A.2.2 lists only the desk as a `merge_reach` consumer; this read is pending that column's update (integrator).
2. Mark each step `agent` or `human`. Human: production deploy, flag flips, money, prod data, external publication, store submission, and a tag push when `release_tags.approval` is `human`. Everything else (staging, consumer simulation, polling) is agent. When unsure, mark `human`.
3. Write `RUN_HOME/release-plan.md` v1 (RUN only, never `plans/<epic>/`): the step table (A.6 R4-J3: `step_id`, step, owner, `tag`); the rollback criteria per step (what is polled, threshold, window); the exact command for each human step. The consumer simulation (G3, design part-04 §5.5) is defined here, skill-locally: one `agent` row of the table (A.6 columns unchanged) for every `publish` and every `tag-push` row, placed before the row it guards, its step text `simulation for <step_id>` naming that row; plan v1 states for it the exact command, the evidence path under `RUN_HOME`, and the pass condition. Its outcome in `release-<sha>.md` is `pass` or `fail`. If v0 has none, add it in v1 with a new unique `step_id` (`^[a-z0-9-]+$`; v0 ids unchanged). Version, tag and publish rows follow `package-release`. Review plan v1 by the run's standard loop (spec §5): first the plan-check loop of `skills/delivery-dispatch-plan/references/plan-check-loop.md` (D55; Plan-checker, design part-03 §3.2) with input `RUN_HOME/release-plan.md` and output `RUN_HOME/pm/plan-check.md` (so the dispatch plan's `RUN_HOME/plan-check.md` stays as it was); read line 1 of that file, never the checker's reply: `PLAN-CHECK: clean` goes on, `PLAN-CHECK: <n> findings` is fixed and re-checked under that page's rules. Then `review-tailor` with `RUN_HOME`, `ARTIFACTS=RUN_HOME/release-plan.md`, `KIND=plan`, `SLUG=run-plan-<n>` (`n` the first with no `RUN_HOME/review-tailor-run-plan-<n>.md`), `STAKES`, `CONTENTION`, `NOVELTY` as the conductor sets them (Inputs), `SECURITY_AUDIT` and `ORCHESTRATOR_TIER` from `RUN_HOME/state.md` `security_audit` and `orchestrator_tier`; an `INPUT-ERROR` from it stops this skill with the same line. Run the `RUNG:` its record names (Rung 1, `doc-reviewer`; G48 before round 1 and after each fix). The adopted review-loop rules (D6), quoted from design part-03 §4 (line 94): "D35 one review orchestrator per loop; D55 plan-check before round 1; D57 freeze scope once the core stops changing (trigger, stated in `review-tailor`: two consecutive rounds with no change to the core sections); D59: an edge enumeration is closed by one check and labelled, and a parked owner item is asked, not re-worded (quoted here because the work environment has no copy of the home file); D60: the same class in two consecutive rounds replaces the mechanism, and the verifier checks the text got shorter, measured in bytes of the affected section (the byte-bar check D65 `RLM:85` is advisory); D62 clerk cadence". Round 3 not clean (D7): write `RELEASE: WAITING-HUMAN` as line 1 of `release-<sha>.md` with the open findings listed, set `stop_reason: d7-round3` (A.3) in `RUN_HOME/pm/substate.md`, run nothing; the owner decides. Do not run any step before the review is clean.
4. Simulation first (G3): before every `publish` and every `tag-push`, run the simulation row that guards it; the request is sent only when that row's recorded outcome is `pass`. A simulation outcome of `fail` never sends the request: record `fail` with its evidence path, set the guarded row's outcome to `not-run`, write `RELEASE: WAITING-HUMAN` as line 1 of `release-<sha>.md` (atomic, as in Step 6) with the failure listed, and stop that row; the human decides (a fix and a new run, or dropping the step), and on resume a failed simulation is not re-run without that decision. A release step ahead of its simulation is stop-the-line `G3`. A publish from the main checkout is `G1`.
5. Run agent steps in plan order. Staging health checks bind nothing; if a step starts a local process, claim the port first (INTERFACES A.5.2, `port-check.sh --claim`, see the `port-claim` skill), record it as a catalog `port` row and register the process with `tools/delivery/catalog.sh` (owner PORT GUARD). After a claim refusal make exactly one retry at candidate+10, claimed before bind, then stop the line (owner OQ-2). At every poll evaluate the step's rollback criteria; a criterion met sets the path to Step 9 (rollback).
6. Human steps. The human action differs by step kind:
   - `publish`, and `tag-push` under `release_tags.approval: human`: the human action is the grant `GATE <run-id> H-prod.<step_id> ok` (B8), which the desk writes as `RUN_HOME/gates/H-prod.<step_id>.<run-id>.ok` (gate-file names carry the run id, A.2.1, AM-5 26). After the grant the agent sends the request (Step 7) and the desk runs the verb (B4). The human does not run it by hand. Owner ruling OQ-3 (2026-10-26): this grant-then-desk path stands under D15 (frozen B4); the desk runs `publish` and `tag-push` only after the `H-prod` grant.
   - Every other human step (production deploy, flag flips, money, prod data, store submission, and the steps above when no desk verb fits): the exact command is prepared in plan v1; the human runs it and reports. Never run it.
   For each waiting step write its row in `release-<sha>.md` (command, `step_id`, outcome `waiting`) and `RELEASE: WAITING-HUMAN` as line 1 (atomic: temp file in the same directory, then `mv`), and stop the step. Never infer a grant; a missing gate file is a wait.
7. Conductor verbs. Allocate `<seq>`, the 4-digit counter (`^[0-9]{4}$`), by an `O_EXCL` create of the marker `RUN_HOME/pm/outbox/.seq/<seq>` for the next free number, a failed create trying the next (C5.1 "Conductor request from the `pm` lead": allocated as for the inbox), then write one line to `RUN_HOME/pm/outbox/<seq>.conductor-request`; one request per file, a fresh `<seq>` for each. The conductor renames it `.sending-<id>`, `.sent-<id>` or `.refused`; never edit those.
   - `CONDUCTOR-REQUEST <run-id> pm <seq> tag-push {"repo":..,"tag":..,"sha":..,"step_id":..}` only if the profile `release_tags.used` is `"yes"` and `tag` matches `release_tags.pattern`, and the guarding simulation row's outcome is `pass`; with `approval: human` wait for `H-prod.<step_id>.<run-id>.ok` first.
   - `... publish {"repo":..,"package":..,"version":..,"step_id":..}` only after `H-prod.<step_id>.<run-id>.ok` exists and the guarding simulation row's outcome is `pass`.
   - `... test-report-push {"tool":"zephyr","payload_path":..,"dry_run":true}` (Zephyr Scale): write the payload to `RUN_HOME/bodies/test-report-<step_id>.json` first; send `dry_run: true` first; send the real request (fresh `<seq>`, `dry_run: false`) only after the dry run's `.out` has `status` `DONE` and the file at its `dry_run_path` (B6) was inspected.
   Results: `.sent-<id>` only means sent; read the result at `RUN_HOME/desk/<id>.out` (C5.1, B6), `<id>` taken from the `.sending-<id>` or `.sent-<id>` suffix of the renamed request file. `.refused` means the conductor refused the line (regex or path); fix the line under a fresh `<seq>`. A desk `REJECTED` is data: record it and handle it per the plan (report, never reroute).
8. Zephyr Cloud read leg (`references/zephyr-leg.md`): confirm each human promotion by the human's report; read the state with `execute` only when `hook-wiring.md` records a working wiring with a positive control at P0 (its refused call asserted by the new line in `zephyr-refusals.log`, not only by the block). Until then make no `execute` call at all. Only operations in `zephyr.read_ops`; the deploy/promote/rollback keyword check is narrowed only at P0 (owner ruling OQ-1, `zephyr-leg.md`) and refuses a colliding read until then. Never call a promote or rollback workflow. A hook refusal is a harness block: stop with `stop_reason: stop-the-line:S1`, report, do not retry or rephrase. A production write that is not recorded is `S7`.
9. Rollback: if a criterion is met on a step an agent ran, undo the staging step and record it; for a production step prepare the rollback command for the human, write `RELEASE: WAITING-HUMAN`, and after the human reports and a read confirms (or the human's report stands, pre-wiring) finish as `ROLLED-BACK`.
10. Write `RUN_HOME/release-<sha>.md`: line 1 exactly `RELEASE: LIVE` or `RELEASE: ROLLED-BACK` (terminal, regex `^RELEASE: (LIVE|ROLLED-BACK|WAITING-HUMAN)$`), then per step: owner, outcome, evidence path, gate file, request seq. Report to the conductor through the `pm` `substate.md`. `WAITING-HUMAN` is never terminal.

## Red flags
| Rationalization | What to do instead |
|---|---|
| "The change is small, I'll run the production deploy." | Production is human. Prepare the exact command, write `WAITING-HUMAN`. |
| "The profile does not require approval, so no gate." | Only a `none` in `release_tags.approval` skips a tag gate; `publish` always needs `H-prod.<step_id>.<run-id>.ok`. |
| "The hook refused a read-looking call; I'll rephrase it." | A refusal is `S1`. Stop and report. Rephrasing is evading the hook. |
| "I can call promote, the human already said yes." | No agent promotes or rolls back in P1. The human runs it; you re-read to confirm. |
| "No wiring is measured yet, but a read is harmless." | No measured wiring means no `execute` call. Fail closed. |
| "Skip the dry run, the payload is the same." | `test-report-push` goes `dry_run: true` first. |
| "`test-report-push` is a Zephyr call, so it goes through `execute`." | It is Zephyr Scale through the conductor and desk; `execute` is the Zephyr Cloud read leg only. |
| "The step id is clumsy, I'll rename it in v1." | Ids are unchanged v0 to v1; gates and requests name them. |
| "Poll later; the criteria passed an hour ago." | Evaluate rollback criteria at every poll. |
| "I will commit plan v1 to `plans/<epic>/`." | RUN only; committing is a human step after CYCLE DONE. |

## Exit criteria
- [ ] `RUN_HOME/release-plan.md` v1 written, `step_id`s unchanged, G48 check run, Rung 1 review clean (or `stop_reason: d7-round3` recorded with `WAITING-HUMAN`).
- [ ] Every human step has its exact command prepared or its grant recorded, and no production command was run by an agent.
- [ ] Every `publish` and every `tag-push` request has its guarding simulation row with outcome `pass` in `release-<sha>.md`; every `publish` and gated `tag-push` request also has its `H-prod.<step_id>.<run-id>.ok`.
- [ ] Rollback criteria were evaluated at every poll; results are in the record.
- [ ] Zero `execute` calls outside `zephyr.read_ops`; every refusal stopped the run and has its line in `RUN_HOME/pm/zephyr-refusals.log` (a refusal with no log line is recorded in `release-<sha>.md` as a wiring defect and reported).
- [ ] `release-<sha>.md` line 1 matches `^RELEASE: (LIVE|ROLLED-BACK|WAITING-HUMAN)$`; `LIVE` or `ROLLED-BACK` before cleanup.
