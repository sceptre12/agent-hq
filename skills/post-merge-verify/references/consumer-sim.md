# Consumer simulation (post-merge-verify)

- Runs after one serial pack (card 12): run the profile `commands.pack` (design part-04 §5.8; `delivery-intake` profile template) once in the worktree, serially, before any consumer row. All consumer-simulation rows use that one artifact; never repack per row.
- Each row installs or links the packed artifact into a throwaway consumer fixture under `RUN_HOME/pm/consumer/<row-id>/` (skill-local path, `DEFAULT`; catalog `tmpdir` row: `catalog.sh register tmpdir <abs path> - run post-merge-verify pm <agent_id>`, then `start`; if the directory cannot be created, `catalog.sh fail tmpdir <abs path>` and stop with reason `tmpdir`), and one runner (A.4 slot row: `persona` `lane-runner`, `unit` `-`, tier `execute`, `budget_min` `durations.unit_median_min`) runs the row's "how it is simulated" text there and writes only `RUN_HOME/pm/evidence/<row-id>.log`. The verify-tier verdict agent compares that log to `expected` and is the single writer of the row's `.line` (SKILL.md Step 10; lead decision, not carried by 1.5.0).
- Install in the fixture uses the profile `commands.install` form (frozen lockfile, scripts ignored). A row that needs a dependency the lockfile does not hold: do not run it, do not improvise; stop with reason `missing-dependency` and report it to the `pm` lead.
- The profile `repo.consumer_repos[]` are read-only here; never edit them.
- Publishing, tagging or promoting the artifact is never part of this skill (`release-track` and the desk own those).
- Class: every consumer row carries a `class` column (`gating|informational`) in the plan's consumer table (template `test-plan.md` §C) and in `postmerge-<sha>.md` (INTERFACES 1.6.0 AM-6 B-9c, the A.6 record format). Step 1 reads it like a §B row's class; the record line carries it as `<class>` (`record-format.md`).
