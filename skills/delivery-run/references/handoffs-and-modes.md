## Sub-task values

The dispatch-plan sub-task table gives `ticket`, `branch` (`<key>-<slug>`) and `repo` (= `REPO`). The sub-task worktree is `<worktree_base>/<run-id>-<subtask>` on `branch`, and each unit worktree is `<worktree_base>/<run-id>-<subtask>-<unit>` (A.6). The PR base is the profile `default_branch` (A.2.2; "main" in the design means this key).

**Sub-task worktree (proposed CV36).** In `build` and `plan-pr`, after reconcile the lead requires the sub-task worktree on `branch` with a `live` catalog `worktree` row. The conductor adds it only before a `claude -p` launch (`skills/delivery-pipeline/references/stages.md:73`; A.8 29-22), so an `agent-tool` lead adds it the same way: `catalog.sh register worktree <path>#<REPO>@<branch>` (`planned`), `git -C <REPO> worktree add <path> <branch>`, then `catalog.sh start`. A failed add is `stop_reason: human`. `pm` is exempt from the sub-task-branch worktree; it adds the detached `<run-id>-pm` worktree in mode `post-merge` step 1 (AM-6 (b)).

## Wave 0, in-lead (C1; part-03 §4 Wave shape)

Wave 0 is not a wave file. The lead runs it before its first `wave-execution` call and before the bus step (`bus-and-ports.md`): the worktree adds are serial, the other steps parallel. Its agents post only to their `status/` files, never to the bus. Each runs as a background Agent call with a slot row, and the lead waits on them in slices of at most 10 minutes with watchdog steps 1-9 between slices, as for hosted skills (`tick.md` "Hosted skills"), so a stalled Wave 0 agent is flagged and stopped like any other (INTERFACES 1.6.0 AM-6 (c): owner answer O3 amends C8 CV1). No bus-reading agent starts before `bus.endpoint` is written.

1. **Catalog check:** done at SKILL.md step 3, before the tick's `cron` row is registered (`catalog.sh register` creates a missing file, so a later check would be vacuous): `RUN_HOME/catalog.tsv` must exist (created empty at stage 3, A.5), else `stop_reason: human`.
2. **Constitution (runs first; A.8 and C8 CV19, S4b; proposed CV45):** only when `PLANS_DIR/subtasks/<subtask>/constitution.md` exists. `delivery-dispatch-plan` writes it at plan time, only for a repo with no profile yet (A.6 writer column; `skills/delivery-dispatch-plan/references/unit-and-waves.md:14`, bundle root next to `waves/`); nothing writes it at run time and the lead never edits it (A.8 "A.6 constitution writer": the bundle root, not under `waves/`; C8 S4b). The lead adds a detached worktree `<worktree_base>/<run-id>-<subtask>-c0` at the sub-task branch head (catalog `worktree` row as in item 3) and dispatches one constitution-and-contracts agent there, with a slot row, the persona the file names and the file as its instruction. With no bus yet, the agent writes its C2 record to `status/<agent-id>.verdict` and the Agent call returns. The lead checks it as a C2 `PASS` read straight from that file: `git -C <c0> rev-parse HEAD` equals `head`, then the file's `done_condition` command when it names one (owner answer O2, item 28 loop record). An Integrator agent (slot row, `unit` `i0`, as in mode `plan-pr`) then lands that head on the sub-task branch, the only branch write (M20). Unit worktrees start from the new sub-task head. `constitution.md` is not a numbered wave (spec-format rule 4, AM-3 errata (d)).
3. **Unit worktrees, serially:** for each unit `u<N>` with no `depends_on`, `git -C <REPO> worktree add --detach <worktree_base>/<run-id>-<subtask>-u<N> <sub-task branch head>`, one at a time (ref and index locks, M13). Register each one as catalog `worktree` (`<abs-path>#<repo-abs-path>@<branch>`), `planned` before the add and `start` after.
   - **Dependent units (C8 S4a, CV44).** A unit with `depends_on` is released only when every blocker has passed its gate AND the Integrator has merged it into the sub-task branch (engine ordering: release = gate pass AND integrated; C8 "C1/C2 release", owner-accepted S4a). Its worktree is cut from the sub-task branch head only then: when the lead appends the last blocker's `INTEGRATED:` entry (`verdicts.md` `PASS` for `i<N>`), it adds the dependent's worktree as above, before the next invocation. So a dependent always starts with its blockers' commits, and the Integrator stays the single branch writer. The release condition is the `wave-execution` EXTEND's to enforce (C8).
4. **In parallel, each with a slot row (`ledger.md`):**
   - the **gate runner** (persona `gate-runner`, mechanical tier) runs the baseline gates on `origin/<default_branch>` under a `gate-runner/<n>` lease. Its result goes to its `status/` file, and no `GATE-PASS` is written (C1);
   - the **Explorer** (persona `explorer`) re-measures the facts, rows in its `status/` file. It runs at mechanical tier by default and at execute tier when the facts need multi-step derivations (AM4-3, D2.1).
5. **Lane leases** for the first invocation (`ledger.md`, C1.1). Set `phase: building` before that invocation (A.8 CV18; the conductor maps it to `building`, A.2).
6. **e2e:** the lead refuses to start e2e generation until `RUN_HOME/<subtask>/gates/H-e2e.<subtask>.<run-id>.ok` exists (A.2.1; gate-file names carry `<run-id>`, AM-5 26). A unit that needs it waits blocked, and the batched `.feature` checkpoint is the human's.

## Integrate (`02-integrate.md`) and `INTEGRATED`

1. The extended `wave-execution` runs waves 1..W in one invocation (W' `skills/wave-execution/SKILL.md` step 6) and takes no stop-after-wave argument, so the controller rolls from `01-build.md` into `02-integrate.md` on its own once every `01-build.md` work_item has passed its gate. The lead therefore sends desk `fetch {repo: REPO, ref: <default_branch>}` and reads its `.out` before **every** invocation (SKILL.md step 10.3; Q5, B4 `fetch` row), and every invocation, also one that resumes inside `02-integrate.md`, runs SKILL.md 10.1-10.8 (proposed CV21). The Integrator rebases onto the fetched remote ref and never sends `DESK`.
   - **Serial `i<N>` (M20).** `02-integrate.md` is a barrier wave unless its work_items carry `depends_on` edges, and a barrier wave dispatches all its work_items at once (W' `references/frontier-mode.md:8-14`). Before the first invocation the lead checks that the `i<N>` work_items form one `depends_on` chain or all name one `lane`; otherwise two writers of the sub-task branch are reachable, and the lead writes `stop_reason: human` and stops (the planner's contract is "merging serially", `skills/delivery-dispatch-plan/references/unit-and-waves.md:20`; proposed CV21).
2. The Integrator is the single writer of the sub-task branch (M20). It posts one C2 record per merged unit, `unit` `i<N>`, with `head` = the sub-task branch head after that merge. For each accepted record (`verdicts.md` `PASS` on the sub-task worktree) the lead appends `u<N> <head>` to `substate.md` `integrated`, which is the `INTEGRATED:` entry, regex `^INTEGRATED: u[0-9]+ [0-9a-f]{40}$` (D1.1).
3. `phase: integrating` from the first `i<N>` dispatch-record line (`tick.md` step 3, proposed CV21). A `merge-conflict` record is `ROLLED`, and a conflict that needs a decision is a stop for the human (card 6 Stop, `architecture/delivery-workflow/part-02-skill-inventory.md:60`).

## Loop end (proposed CV21)

- An invocation re-dispatches every work_item its checkpoint does not record as gate-passed (W' `SKILL.md:190-196`), escalated ones included. So while any unit has an open escalation (C2 `ESCALATE`, a drained `fix-loop-cap-exhausted`, a blocked unit, a paused head-mismatch unit; open and closed per `verdicts.md` "Escalation closure", proposed CV34) the lead starts no invocation, for any unit: it waits for the `ANSWER` (`tick.md` "Wait states"), with `phase` unchanged and `stop_reason` empty. A `ROLLED` tier-up of another unit waits too. "The rest of the sub-task runs on" (CV6) means only inside the invocation that raised it.
- When the loop ends the lead sets `phase: prepr` at once, so the loop end is persisted and the tick's pending-dispatch gate never re-enters it (`tick.md` step 9a).
- After a return, the lead reads that invocation's `dispatch/<invocation>.jsonl`. A file with no line means the controller found nothing to run (W' `SKILL.md:202`, "All passed: report complete and exit without bus or dispatch"): with every unit's `u<N>` in `integrated`, the loop has ended and the lead goes to `pre-pr-gate`; otherwise the return made no progress, and the lead writes `stop_reason: human` and stops instead of re-invoking. A file with lines means progress: the loop goes on.
- The checkpoint stays the authority for what passed (O-Q6). It lives at `PLANS_DIR/subtasks/.wave-execution-state/<hash>.json` (the parent of the bundle-root `spec_root` `PLANS_DIR/subtasks/<subtask>/`, `skills/wave-execution/SKILL.md:190`; INTERFACES 1.7.0 AM-7 touch-up 6, E46; one hash per sub-task, since `session_id` differs), so the lead never picks one by age; it reads only the dispatch record and its own accepted records.

## `pre-pr-gate` (D2.2 row 10)

- **Before each call:** desk `fetch {repo: REPO, ref: <default_branch>}`, then read its `.out` (Q5).
- **Inputs:** `RUN_HOME`, `SUBTASK`, `HEAD` (the sub-task branch head: the last `integrated` head, or the CI-fixed sha below), `WORKTREE` (the sub-task worktree), `REPO_PROFILE` (`@<sha>`), `SECURITY_AUDIT` (passed on unchanged). Set `phase: prepr` first. Hosting rules (own Agent calls, background slices, deadlines): `tick.md` "Hosted skills" (proposed CV22).
- **Reserved and slots:** its review seats run under `review: 10`; its other agents get rows (`ledger.md`, PC-W2-6).
- **Output:** `RUN_HOME/review/<subtask>/checklist-<subtask>.md` line 1, regex `^PREPR: (PASS|STOP( [A-Za-z0-9.,-]+)?)$`. Store only the word after `PREPR: ` up to the first space in `substate.md` `prepr` (`PASS` or `STOP`, A.3; the desk cross-checks `prepr: PASS`), set `head` to the gate's head, and set `review_record` to `RUN_HOME/review/<subtask>/record-<head>.md`. All three name the same sha.
- **`PREPR: STOP`:**

  A second review-bus port refusal is `PREPR: STOP C12`, with the refusal line recorded in the checklist (`skills/pre-pr-gate/SKILL.md:124-126`; settled point 5, `skills/pre-pr-gate/references/steps-detail.md:64`; D2.2 row 10, AM-6 B-7). C12 also carries the reviewer-record condition, and its stop text says which failed (AM-7 touch-up 5). The lead classifies, first match wins (proposed CV26):

  | Evidence | `stop_reason` |
  |---|---|
  | line 1 is `PREPR: STOP C12` and the C12 row's stop text names the port condition (the recorded refusal line), not the reviewer record | `port-refused` (D2.2 row 10, Q3, AM-4 W2-1) |
  | a `RUN_HOME/review/<subtask>/verify-*-3.md` written by this call exists (round 3, `steps-detail.md:38,56`) | `d7-round3` (D7) |
  | anything else, a C12 reviewer-record failure included | `stop-the-line:S2` (a failed gate) |

  The lead stops and the conductor reports.
- **`INPUT-ERROR` from `pre-pr-gate`** (or from any skill the lead invokes) carries no verdict. It is not a D7 round and not a fix-verifier iteration. The lead fixes the input and re-invokes with the same iteration (AM4-2, `architecture/delivery-workflow/tasks/28-delivery-run.md:133`; D1).

## Stage 5: desk requests, in this order (B4)

Each request waits for its `DONE` `.out` before the next (`control-channel.md` for sending and polling).

1. **`push` `{repo, branch, expect_head: head}`.** The first push of the PR needs `PREPR: PASS` for that head and `gate-runs/<head>.md` (`GATE-PASS`, A.7; the `pre-pr-gate` cold run is that record). No push precedes `pre-pr-gate` (r3 H26). The desk adds `HUSKY=0` inline; the lead never skips hooks itself.
2. **`pr-create` `{repo, branch, base: <default_branch>, body_path: RUN_HOME/review/<subtask>/pr-body.md, labels[], record_path: <review_record>, expect_head: head}`**, sent only after `prepr: PASS` for `head` (A.3). Copy `pr` from the `.out` to `substate.md` and set `phase: pr-open`.
3. **`pr-attach` `{repo, pr, paths[]}`**, right after `pr-create`, with the lane artifacts under `RUN_HOME/<subtask>/lanes/`. It is skipped when `lanes/` holds no file.
4. **`pr-comment` `{repo, pr, body_path}`**, with a body under `RUN_HOME/bodies/` listing the URLs `pr-attach` returned. It never approves.

**Later pushes to the same PR** (CI fix rounds, through `ci-fix-loop`) need the `GATE-PASS` record for their head plus either `RUN_HOME/ci/<pr>.md` naming that head or `PREPR: PASS` for it (AM4-1, AM-4 24-Q2). They only fast-forward. `ci-fix-loop` writes `ci/<pr>.md` line 1 only at its Finish step (`skills/ci-fix-loop/SKILL.md:36`), and the desk accepts any line of that file containing `expect_head` (`skills/delivery-desk/references/verbs.md:48-50`). So before relaying each `ci-fix-loop` push the lead appends one line `push-head: <expect_head>` to `ci/<pr>.md`, creating the file when absent; line 1 stays `ci-fix-loop`'s, and the lead copies line 1 only after `ci-fix-loop` returns (proposed CV27).

## `ci-fix-loop` (D2.2 row 11)

- **Inputs:** `RUN_HOME`, `SUBTASK`, `REPO`, `PR`. Set `phase: ci`. Its diagnoser, fixer, G48 checker and fix-verifier run one at a time under `ci: 1`, and its gate runner gets a row (PC-W2-6). Its `DESK` lines go through this lead (B1).
- **Output:** `RUN_HOME/ci/<pr>.md` line 1, regex `^CI: (GREEN [0-9a-f]{40}|HUMAN [a-z0-9-]+)$`. Store the text after `CI: ` in `substate.md` `ci` (`GREEN <sha>` or `HUMAN <reason>`, A.3).
- **`CI: GREEN <sha>`:**
  - `<sha>` = `head`: done. Wait for `MERGED`; the conductor merges once it reads `pr`, `ci: GREEN <sha>`, `prepr: PASS`, `head` = `<sha>` and `review_record` = `record-<sha>.md` (A.3 W2-7).
  - `<sha>` differs from `head` (CI fixes moved the head): `fetch`, then re-run `pre-pr-gate` with `HEAD=<sha>`. Its step 1 delta verify covers the change, and `prepr`, `head` and `review_record` then name `<sha>` before the conductor can merge (PC-W2-3).
  - That re-run's fix rounds can move the head again (`skills/pre-pr-gate/SKILL.md:128,135`). Then the lead later-pushes the new `head` (it has `GATE-PASS` and `PREPR: PASS`), re-runs `ci-fix-loop`, and repeats until `ci` names `head`. A third such cycle is `stop_reason: d7-round3` (D7 bound applied to this cycle, proposed CV28).
- **`pending`:** the bound on `ci-status` `pending` is in `tick.md` "Hosted skills" (proposed CV22).
- **`CI: HUMAN` mapping (PC-W2-4):**

  | `ci/<pr>.md` | `stop_reason` |
  |---|---|
  | `CI: HUMAN policy` | `stop-the-line:D23` |
  | `CI: HUMAN d7-round3` (its round-3 stop; the line 1 status, never the findings below it) | `d7-round3` (A.8 "A.3 `stop_reason`", 28 post-D7; INTERFACES 1.6.0 AM-6 spec 28) |
  | any other `CI: HUMAN` | `human` |

  `ci-fix-loop` step 9 writes `CI: HUMAN d7-round3` at its round-3 stop (`skills/ci-fix-loop/SKILL.md:33`, erratum E41), so the lead keys the `d7-round3` mapping on that line 1 token alone, not on a `verify-*` file.

## `MERGED` -> `delivery-cleanup` (C5.1, D2.2 row 9)

- On inbox `MERGED <subtask> <merge_sha>`: set `phase: merged` and run `delivery-cleanup` with `RUN_HOME`, `MODE=subtask`, `SUBTASK`, `MERGE_RECORD=RUN_HOME/merge-<merge_sha>.md`. The lead is the approver; the executor is a separate mechanical-tier agent with a slot row. Cleanup removes the bus, pm2 app, port claim, worktrees, the cron and the leases through their catalog rows.
- After `cleanup-<run-id>-<subtask>.md` line 1 reads `CLEANUP DONE <subtask>`: set `phase: done`, rename the `MERGED` inbox file `.consumed` (only now, so a crash replays it; proposed CV38), write `substate.md`, print its path, and end.
- **Cleanup fails** (`delivery-cleanup` step 8: `SPOT-CHECK FAIL`, or no final record appears): write `escalations/cleanup.md` with reason `human-step` and the `cleanup-<run-id>-<subtask>.md.tmp` path, write `stop_reason: human`, print the escalation path and the `substate.md` path, and stop (proposed CV39). `phase` stays `merged`.
- **`pm` cleanup:** the `pm` lead runs `delivery-cleanup` mode `subtask` with `SUBTASK=pm` once `release-<pm_sha>.md` line 1 is terminal (`RELEASE: LIVE` or `RELEASE: ROLLED-BACK`). Its evidence is `postmerge-<pm_sha>.md` and `release-<pm_sha>.md`, the `substate.md` `postmerge_record` and `release_record`. There is no `MERGE_RECORD`.

## Ticket events (R-5)

The lead's hand-off to `ticket-clerk` is its `substate.md` fields (`phase`, `prepr`, `ci`), which the conductor turns into ticket events. The lead never invokes `ticket-clerk` and never sends any `jira-*` verb.

## Mode `plan-pr` (`st0`; A.2)

There is no seed, no waves and no bus. `substate.md` is initialized from `subtask_id`, `session_id`, `phase: seeded`. After reconcile:

1. Copy the `PLANS_DIR` files onto the `st0` branch in the sub-task worktree (A.6 dispatch-plan additions). The copy-and-commit is done by one Integrator agent the lead dispatches (slot row), because the branch has a single writer (M20). Dispatch details (proposed CV40): slot row `unit` `i0`, `worktree` the `st0` sub-task worktree, `budget_min` `durations.unit_median_min`; the instruction is "copy the `PLANS_DIR` files the A.6 dispatch-plan additions list onto `branch` in `<st0 worktree>`, commit once, and write your C2 record with `unit` `i0`". There is no bus in `plan-pr`, so the Integrator writes its record to `status/<agent-id>.verdict` (its brief's bus-unreachable fallback) and the Agent call returns. The lead then takes `HEAD` = `git -C <st0 worktree> rev-parse HEAD`, which must equal the record `head` (C2 `PASS`), and frees the row.
2. Then `fetch`, `pre-pr-gate`, stage 5, `ci-fix-loop`, `MERGED` -> `delivery-cleanup`, as above.

## Mode `post-merge` (`pm`; A.2 stages 6-7 host)

There is no seed, no waves and no bus. `PM_SHA` is required.

1. Initialize `substate.md` as in `plan-pr` (with the `reserved` map, proposed CV29), and record `pm_sha`. As its first step the lead adds the detached worktree `<worktree_base>/<run-id>-pm` at `PM_SHA`: `catalog.sh register worktree '<path>#<primary_repo>@main' ...` (`planned`), `git -C <primary_repo> worktree add --detach <path> <PM_SHA>`, `catalog.sh start` (a failure: `catalog.sh fail`, `stop_reason: human`); `post-merge-verify` Step 2 then finds and reuses it (INTERFACES 1.6.0 AM-6 (b); the 29-22 worktree-add exemption covers only the sub-task-branch worktree). The `pm` lead's work runs in that detached post-merge worktree at the merge sha, never in the main checkout (A.8 "A.2 merge order and `pm` host", s7-4; A.6). A second `pm` lead that finds a fresh `substate.lock` refuses to start with `stale-session` (`resume.md` "Lifetime lock"; A.8, owner item O-1's lead default).
2. Run `post-merge-verify` (`RUN_HOME`, `PM_SHA`, `PLANS_DIR`, and inline `WORKTREE_BASE` = the profile `worktree_base` and `REPO_PROFILE` = the lead's own input; `skills/post-merge-verify/SKILL.md:13`; D8 "D2.2 row 12"), with `phase: post-merge`. Its verdict arrives as a `verdict` inbox file written by its verdict agent (`control-channel.md`; C8 "C5.1 inbox"; INTERFACES 1.6.0 AM-6 (a): the desk writes no `VERDICT` line, except the human-decision `VERDICT`, 1.7.0 AM-7 touch-up 7 (B8, C8), step 5). A destructive row runs only with `RUN_HOME/gates/H-destructive.<row-id>.<run-id>.ok` (A.2.1, desk-written on `GATE H-destructive.<row-id> ok <text>`, B9); without it `post-merge-verify` stops (step 5 below). Copy `postmerge-<pm_sha>.md` line 1 into `postmerge` (the bare `PASS` or `FAIL`) and its path into `postmerge_record`.
3. On `POSTMERGE: PASS`, run `release-track` (`RUN_HOME`, `PM_SHA`, `PLANS_DIR`, `POSTMERGE_RECORD`, `REPO_PROFILE`, `STAKES`, `CONTENTION`, `NOVELTY`), with `phase: release`, and record `release_record`. `release-track` Step 0 requires the last three (`skills/release-track/SKILL.md:17`). The lead reads them from the fixed header block of `PLANS_DIR/review-architecture.md`, lines 2-4 after `ARCH: ready`: three `key: value` lines `STAKES:`, `CONTENTION:`, `NOVELTY:`, which `delivery-architecture` writes (`skills/delivery-architecture/references/review-handoff.md:21-25`; D8 "D2.2 row 3 output": three `key: value` lines in a fixed header block of `review-architecture.md`, consumed by rows 5 and 13; C8 "Stage 8 read-back ... and `pm` inputs": lines 2-4 of `PLANS_DIR/review-architecture.md`, absent means no `pm` launch). For each one absent or outside its D2.1 enum it prints `INPUT-ERROR <NAME> missing|enum` (D1), writes `stop_reason: human`, prints the `substate.md` path and stops before `release-track`. Its conductor-only verbs leave through `RUN_HOME/pm/outbox/<seq>.conductor-request` (C5.1); the lead sends none of them.
4. On `POSTMERGE: FAIL` (proposed CV32): `postmerge: FAIL`, `phase` stays `post-merge`, `stop_reason` empty; before it ends the lead runs `delivery-cleanup` mode `subtask` with `SUBTASK=pm` (evidence `postmerge-<pm_sha>.md`, no `MERGE_RECORD`), so the `<worktree_base>/<run-id>-pm` worktree, its ports and its tick cron are gone before a second `pm` lead runs `post-merge-verify` Step 2 on a new `PM_SHA` (owner answer to R2-19; A.8 "A.2 merge order and `pm` host": the old `<run-id>-pm` worktree must be gone before a second `pm` lead). A cleanup failure is the CV39 stop. Then it prints the `substate.md` path and ends. The re-entry (new `st<N>` from `pm/new-units.md`) is the conductor's (A.2).
5. On `POSTMERGE: STOP <reason>` (D8 "D1.1 tokens", `^POSTMERGE: (PASS|FAIL|STOP [a-z0-9-]+)$`; `skills/post-merge-verify/SKILL.md:50`): leave `postmerge` empty, set `postmerge_record`, write `stop_reason: human` (A.8 reads a `pm` `human` beside a `POSTMERGE: STOP` record as that row), print the record path and the `substate.md` path, and stop. For `STOP product-decision` the owner answers at the desk, which writes the `pm` inbox `verdict` file `VERDICT pm <row-id> <text>` (`control-channel.md`; INTERFACES 1.7.0 AM-7 touch-up 7, E47); after the desk-written `RESUME.pm` gate (A.8) the lead, back in `phase: post-merge`, re-runs step 2 for the same `PM_SHA`.
6. On `RELEASE: WAITING-HUMAN` (not terminal, `skills/release-track/SKILL.md:37`): wait per `tick.md` "Wait states"; while `stop_reason` is empty every tick re-invokes `release-track`, which resumes at its Step 0 (proposed CV25). No lead-side timer bounds it: the owner is the bound, and the conductor lists the wait in every status post (owner answer O6, item 28 loop record).
6a. **`release-track` stops.** Any stop `release-track` reports (`S1` hook refusal, a `G3` simulation `fail`, `S7`, `d7-round3` recorded with `WAITING-HUMAN`; `skills/release-track/SKILL.md:24,35,44,54`) is written by the lead to `substate.md` `stop_reason` as reported (`stop-the-line:<id>` or `d7-round3`); the lead prints the `release_record` and `substate.md` paths and stops, and step 6 no longer re-invokes (proposed CV25).
7. On a terminal `RELEASE:` line, run the `pm` cleanup above.

## `.decisions` fork flow (template `references/templates/decisions-fork.md`)

1. A unit that hits its Decision Gate writes `.decisions/<unit>.md` per the template, then posts `ESCALATE` `decision-gate`. The lead writes `escalations/<unit>.md` with that path (`verdicts.md`).
2. The lead reads the Fork, Options and Recommendation and never edits them. It resolves the fork itself (`resolved_by: lead`) only when the fork stays within the plan and the frozen contracts. A fork that touches an owner ruling or a one-way decision goes to the human, and the escalation stays open.
3. The human's answer arrives as inbox `ANSWER <run-id> <subtask> <unit> <text>`. The lead writes the Resolution with `resolved_by: human`, quoting the text.
4. The lead fills `## Re-dispatch instruction`: the exact value, the file, and the tier (`tier_override <unit>=<tier>` if raised). Until that section is filled the unit stays blocked. Once it is filled, the escalation closes (`verdicts.md` "Escalation closure", proposed CV34).
5. **Delivery to the worker (proposed CV42).** The re-dispatched worker reads only `.tasks/<unit>-<slug>.md` and its frozen instruction (`references/briefs/implementer.md:9`), so the lead appends one line `Decision: <abs path of .decisions/<unit>.md>` (or, for a non-fork answer, `Answer: <abs path of the escalations/<unit>.md.resolved-<ts> file>`) to the unit's `.tasks/<unit>-<slug>.md`. That file is outside `spec_root`, so the checkpoint hash is unchanged.
6. Re-dispatch is a fresh invocation, once the live one has returned (`ledger.md`). The controller resumes at the unpassed items.
