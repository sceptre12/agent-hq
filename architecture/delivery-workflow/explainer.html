Explainer for leadership

How a software change travels through the agent team

A request for a change goes in one end. A reviewed, tested, merged and released change comes out the other. People step in only at a few doors along the way.

Based on the written design and on the first full pilot run (October 2026). Numbers are measured, not estimated.

The idea in one sentence

A delivery line for software, with a few doors

Describe what you want changed. The agent team plans it, builds it, checks it, gets it reviewed, merges it and releases it. A person decides only at four doors.

Everything between the doors runs on its own. The people's job is to say "yes, that is what I meant" at the start, "yes, that design is right" before building, "yes, this change can go in" before merging, and "yes, put it live" at the end. In the first pilot run the "Change OK" door (a person reviewing the pull request) was waived; the other three doors ran.

The cast

Who is on the team, and who is allowed to do what

Most of the team works inside a sealed workspace (a "sandbox": a locked room where software can run but cannot reach the internet or install anything new). One role, the desk, sits at the wall and is the only one that touches the outside world. That split exists for a reason: anything that reads the open internet can be tricked by text it finds there, so that risk is confined to one carefully watched seat.

Person

The owner

Asks for the change and decides at the doors. Proposed for the next run: type a delegation once and the team reads it from a signed record. Today the owner types each decision at the desk.

Agent, at the wall

The desk

The only agent allowed to act outside the sandbox: push code, open and merge pull requests, update the work tracker, research on the web, install software. Every action is checked against a fixed set of rules first.

Agent

The conductor

Runs the whole journey from first question to release. Keeps the master status file and decides which stage comes next.

Agent

Team leads

One per sub-task (a slice of the work that becomes one pull request). Each lead runs its own crew of up to 30 builders and checkers at once.

Agents, many

Builders and reviewers

Short-lived helpers. One writes the code or test for a single work item; a different one checks it; seven more review the finished change.

Memory

Hermes

The team's shared memory. Every run writes down what it learned, so the next run starts smarter rather than from zero.

How quality is enforced

Nobody grades their own homework

Every piece of code is built by one agent, checked by a different one and reviewed by seven more before it can be merged, and the merge itself needs a signed record proving that it did.

What we learned

Three changes for the next run

Every stop in the pilot was one of three things: a setup item that was missing, a permission a person had to type again, or a hand-off between sessions that added waiting. Each gets a fix.

Change 1

Pre-run checks

Before the first door opens, a checker confirms every setting, folder, tool copy and option list is in place, and refuses to start otherwise. The pilot lost about 70 minutes to items that would have failed this check.

Change 2

One trust line

The owner types a single delegation line at the desk before the run. It names who may answer which doors, and every session reads the same signed record. No more re-typing the same permission in each session.

Change 3

Fewer hand-offs

Shorten the one-after-another design reviews, give the desk clear standing permission for the exact one-way actions the plan allows, and keep more of the work inside self-contained teams.

Glossary

Ten terms, in plain words

Agent
A piece of software that can read, write and run things on its own to finish a task it has been given.
Sandbox
A locked room for software: it can run and change its own files, but cannot reach the internet or install anything new.
Desk
The one agent allowed outside the sandbox. It acts for the team on the code host, the work tracker and the web, following fixed rules.
Conductor
The agent that runs the whole journey, stage by stage, and keeps the master status file.
Sub-task
A slice of the work small enough to become one pull request, built by its own team lead and crew.
Pull request (PR)
A proposed change to the code, shown side by side with the old version so it can be reviewed before it goes in.
Merge
Accepting a pull request so its change becomes part of the main code line.
Automatic checks (CI)
Tests and scans that run by themselves on every proposed change and report green or red.
Door (gate)
A point in the journey where a person must say yes before the agents continue.
Finding
A problem a reviewer wrote down, graded by how serious it is. Serious ones must be fixed before the change can move on.
