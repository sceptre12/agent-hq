- (29-1, adopted, A.8) A.1 `session` token shapes: a lead's launcher session is `<run-id>-<subtask>-l<n>` (`n` the launch count for that sub-task, from 1); the conductor's is `<run-id>-c<n>` (`n` the count of conductor sessions for the run); both inside `^[a-z0-9-]+$` and distinct from the bus `session_id`.
- (29-2, adopted, A.8) A.4 conductor launch check: a new lead counts 31 against the machine ledger (at most 30 slot and reserved agents plus its own seat, the W2-9 `live_count`), so a launch is allowed only when `sum(live_count) + 31 <= 200`; rule 8 allows a `MODE=build` launch only when at most 2 rows carry `build=1`; `plan-pr` and `post-merge` leads write `build=0`.
- (29-3, adopted, A.8) A.2 run-level `stage` while sub-tasks move in parallel: `1`-`3` run-wide; from the first lead launch until the `pm` lead starts, `stage` is the least advanced stage over the sub-tasks not yet `cleaned`, mapped from `substate.md` `phase` (`seeded|building|integrating` -> `4`, `prepr` -> `4b`, `pr-open|ci` -> `5`, `5a` once `ci: GREEN <sha>` is read and the H-pr read-back is not yet true, `5b` while the conductor's `pr-merge` is in flight, `merged` -> `5c` until `CLEANUP DONE <subtask>`); `6` and `7` follow the `pm` lead's `phase`; `8` from `CLEANUP DONE final`.
- (29-4, adopted, B9) B1, C5.1 "run log": a refused relay (`<id>.desk.refused`) and a refused `CONDUCTOR-REQUEST` (`.refused`) are logged as one line in the conductor's turn output (the session transcript) plus a status-post line; no run-log file is written under `RUN_HOME`.
- (29-5, not adopted: owner item O-1, lead default pending the owner; INTERFACES.md "Owner items from the item 29 panel") A.2 stages 6-7 host on post-merge re-entry, as A.8 records it: the existing `subtasks[]` `pm` entry is reused with a new `session`; the second `pm` lead is launched only once the old `pm` lead's `substate.lock` is gone or stale (C5.3 lock rule), with `PM_SHA` = the re-entry sub-task's `merge_sha` and a fresh inbox `RELEASE pm`, which sets the entry `state: released` again. Lead default for O-1: a second `pm` lead that finds a fresh `substate.lock` refuses to start with `stop_reason: stale-session` (A.8).
- (29-6, not adopted: owner item O-2, lead default pending the owner; C8 "C5.3 relaunch limits" with CV47) C5.3 relaunch limits: at conductor resume the dead-lead check also covers `merged` sub-tasks not yet `cleaned` (their lead still owes `delivery-cleanup` mode `subtask`); a lead that dies again after one relaunch before its `phase` advances is reported to the owner, not relaunched a third time. Lead default for O-2: the check covers those sub-tasks, but a relaunch there runs only `delivery-cleanup` `MODE=subtask`. A `claude -p` lead that exits cleanly in a wait with no invocation live (28-CV47, owner answer O5) is not a dead lead and is relaunched on its waking inbox file or the next tick (`resume.md` §Lead relaunch).
- (29-7, adopted, B9) B1 no-reply for the conductor's own requests (`pr-approval-state`, `pr-merge`): after the 5 + 5 minute wait the conductor renames `<id>.req` to `<id>.req.noreply`, treats it as terminal `sender` and posts it as a human step in place of the C2 escalation (a C2 record is per unit; the conductor's request belongs to no unit).
- (29-8, adopted, C8) D3 `blocked` on escalations: a file under `RUN_HOME/*/escalations/` or `RUN_HOME/escalations/` gets `blocked` when its ticket has no `blocked` event in `ticket-events.log` since the file appeared (re-derived after a crash, 29-15), (the skill keys `blocked` on `ticket-events.log` as C8 29-15 requires; C8's 29-8 line words "new" as "not listed in the previous post", which the skill uses for posting only), and `ticket-clerk` absorbs a repeat `blocked` for a ticket already `Blocked`.
- (29-9, adopted, D8) D2.2 row 1, card 1 missing state at resume: a `RUN_HOME=` under `$DELIVERY_ROOT` without `state.md` prints `INPUT-ERROR RUN_HOME path`, an unparsable one `INPUT-ERROR RUN_HOME format`; the conductor then prints a rebuild report derived from the row files (`*/substate.md`, `merge-*.md`, `cleanup-*.md`, `gates/`, `tickets.tsv`, `desk/*.out`, the dispatch plan), writes nothing, and stops until the owner decides.
- (29-10, adopted, B9) B1 applied-result scan order at conductor resume: the scan (local writes only: `merge-<sha>.md`, `merge_sha`, `MERGED` and due `RELEASE` inbox files, `gates.H-pr`) runs before every send, the `REGISTER-SENDER` re-send included.
- (29-11, adopted, A.8) A.2 `security_audit` input errors: a missing `security_sensitive:` line in `architecture.md` is `INPUT-ERROR security_sensitive missing`; two such lines, or a value other than `yes|no`, is `INPUT-ERROR security_sensitive format`.
- (29-12, adopted, A.8) A.2.1, B5 H-pr pointer: the conductor records `gh:<owner>/<repo>#<pr>@<commit_id>` in `gates.H-pr` only when the `pr-approval-state` result has `h_pr` true and `headRefOid` equal to the sub-task's `ci: GREEN <sha>`; otherwise it asks again on a later tick.

- (29-13, adopted, A.8) Launch intent before exec: before a lead is started (first launch or relaunch) the conductor runs every fail-closed check (and the worktree add), then writes, in one `state.md` write, `session` (`<run-id>-<subtask>-l<n>`, so `n` is the stored launch count), `launched_utc`, `state: released` when it is released at launch, and `relaunch_phase` (the `substate.md` `phase` at a relaunch, empty at the first launch); only then execs. A sub-task whose `session` is set is never launched again under that token; what it counts in the launch sum is 29-26. A launched lead with no `substate.lock` newer than `launched_utc` and no `register.consumed` 10 minutes (default) after `launched_utc`, with no launch pid file (`homes/<session>/pid`) or one that fails `kill -0`, is a startup failure: post the `lead.log` path as a human step and apply the one-relaunch rule. A second death with `phase` still equal to `relaunch_phase` (launch count `n` >= 2 since the last phase change) is posted to the owner with the sub-task, both session tokens, `lead.log` and `substate.md` paths; no further relaunch.
- (29-14, adopted, C8) Due inbox messages are re-derived from `state.md` on every tick and at resume, never only at the event that made them due: each message is keyed on the current cycle as 29-25 states (`RELEASE <s>` and `RELEASE pm`, `MERGED <s> <sha>`, `INVALIDATE <s> predecessor-reentered`; C6; the merge-order rule 29-18 governs merges, not releases). A back-edge writes the predecessor's `reentered: true`, `reentered_utc` and clears `merge_sha` in one `state.md` write before any `INVALIDATE` file. A due message is written once (the inbox file is the record), so a crash between any two writes is repaired by the next tick.
- (29-15, adopted, C8) Every wait is entered by printing the status post and ending the turn; the session cron prompt is `delivery-pipeline tick <RUN_HOME>`. Each tick, after reading files, the conductor also: continues a stage whose gate file or exit token appeared (H0, H1, `ARCH: ready`, `PLAN-CHECK: clean`), launches ready sub-tasks, runs the stage 5b readiness check, and posts every stop, escalation, refusal or human step that is new since the previous post (new = not listed in the previous post; after a resume every open item is new once). `TICKET-EVENT <key> blocked` and `unblocked` are derived from `RUN_HOME/ticket-events.log`, never from the previous post: `blocked` for an open escalation file whose ticket has no `blocked` event since the file appeared; `unblocked` when a ticket's latest event is `blocked` and no open escalation, blocking `stop_reason` or unanswered `INVALIDATE` remains.
- (29-16, adopted, B9) Every conductor send has one no-reply rule (B1 5 + 5 minutes, default): `REGISTER-SENDER`, its own `pr-approval-state`/`pr-merge`, and each relayed `CONDUCTOR-REQUEST` (`.sent-<id>`): poll the reply or `RUN_HOME/desk/<id>.out`, re-send the same line or id once, then post it as a human step (`<id>.req.noreply` for requests); a terminal `REJECTED` `.out` of a relayed request is posted too. Before minting a request id the conductor adopts an own `RUN_HOME/desk/*.req` with the same verb and fields and no `.out` (a crash between `desk-req.sh` and the `.sending-<id>` rename), so one request never gets two ids. A terminal `pr-merge` `REJECTED` `.out` or a `.req.noreply` for a sub-task's current `head` blocks that sub-task's 5b readiness (the file itself is the marker) until the human clears its cause; the resume scan re-posts both. Until the desk answers `REGISTERED <run-id> | run | ok` (stage 1 claim, or after `REBIND` at resume) no tick or stage step, except the `run` claim and its re-send (29-27), sends, relays, renames, launches a lead or runs `ticket-clerk`; the tick reads files and writes `state.md` and inbox files only.
- (29-17, adopted, A.8) Stage re-entry at resume and after `H1.changes`: a stage skill is skipped when its exit artifact exists and is current: stage 1 `gates/H0.ok` plus a `repo_profile` (re-derived as `<profile path>@<sha>` from the profile file when the field is empty); stage 2 `ARCH: ready` plus an `H1` file not yet handled; stage 3 a clean `plan-check.md` with `subtasks[]` filled. An `H1.*` file is handled once: the conductor records `h1_handled: <name> <utc>` from the file's `utc=` only after the `delivery-architecture` re-invocation returns, treats H1 as pending again only when the live H1 file's name or `utc=` differs, and skips stage 2 after an `H1.changes` only when `review-architecture.md` is newer than its `utc=`. After `gates.H1` is recorded, `epic` empty or `tickets.tsv` absent re-runs `ticket-clerk` and the epic copy before stage 3.
- (29-18, adopted, A.8) Merge order (D5): the predecessors of a sub-task for the 5b merge precondition and `pr-merge` `predecessors[]` are every sub-task with a lower dispatch-plan `merge order` (`st0` first), not only its `depends-on` rows; `RELEASE` follows `depends-on` (C6).
- (29-19, adopted, A.8) The `pm` host: its `subtasks[]` entry takes `repo` = `primary_repo` and `backend` = the `st0` backend; the `pm` lead runs in the detached post-merge worktree at the merge sha, never the main checkout (s7-4, owner D7 stop; A.8). `CLEANUP DONE pm` maps to `state: cleaned` only once `release_record` line 1 is terminal. The dead-lead relaunch skips a `pm` whose `postmerge` is `FAIL`, whose `postmerge-<pm_sha>.md` line 1 is `POSTMERGE: STOP <reason>`, or whose `release_record` is terminal. Before a second `pm` lead the old `<worktree_base>/<run-id>-pm` worktree must be gone: the conductor runs `delivery-cleanup` `MODE=subtask` `SUBTASK=pm` with the `POSTMERGE: FAIL` record; if `delivery-cleanup` refuses that evidence (it now asks for a terminal release record, question for its owner), the conductor posts the worktree path and catalog row as a human step and waits.

- (29-21, adopted, A.8) The network-write tool list for `--disallowedTools` is read from `$DELIVERY_ROOT/launcher/disallowed-tools.txt` (one tool name per line, written at the move); absent or empty is `INPUT-ERROR launcher.disallowed_tools missing` and no launch.
- (29-22, adopted, A.8) The conductor adds the sub-task worktree before a `claude -p` launch (the lead adds only unit worktrees): catalog `register worktree` `planned`, `git -C <REPO> worktree add <worktree_base>/<run-id>-<subtask> <branch>` (the dispatch-plan `branch`; `-b` from `origin/<default_branch>` when it does not exist), then `start`; the child runs with that directory as cwd. `pm` is exempt (its lead adds the detached worktree).

- (29-24, adopted, C8) Stage 8 read-back verdict: the read-back agent writes `RUN_HOME/capture/read-back.md` line 1 `READ-BACK: pass` or `READ-BACK: <n> differences`; on differences the conductor fixes `retro.md`/`execution-log.md` once and re-runs a fresh read-back; a second failure goes to the owner in the final post; the final post names `RUN_HOME/capture/`.
- (29-25, adopted, C8 and A.8) Cycle keys for re-derived inbox messages and applied results: `state.md` carries per sub-task `released_utc` (set on every `RELEASE`), `launched_utc` (29-26) and `reentered_utc` (set with `reentered: true` at a back-edge, kept). `RELEASE <s>` is due when every `depends-on` predecessor has `merge_sha` and no `release` file is newer than `<s>`'s latest `invalidate` file; `RELEASE pm` when the `pm` entry has `session` set, every other sub-task has `merge_sha`, and no `release` file is newer than the `pm` `launched_utc`; `MERGED <s> <sha>` when no `merged` file names the current sha; `INVALIDATE <s> predecessor-reentered` when `<s>`'s `released_utc` precedes the predecessor's `reentered_utc` and `<s>` has no `invalidate` file newer than it.
