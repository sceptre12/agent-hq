# Merge pipeline via desk `ci-status-main` (post-merge-verify)

Contracts: INTERFACES part-b B1 (`.out` polling), B2 (line grammar), B2.1 (reason classes), B3 (request file), B4 (`ci-status-main` `{repo, merge_sha}`; result `merge_sha`, `stages[] {name, state}`, `state` as `ci-status`); part-c C5.2 (channel per backend).

## Request
1. Fields file `RUN_HOME/pm/ci-status-main.fields.json`: `{"repo": "<primary_repo>", "merge_sha": "<PM_SHA>"}`. Never a PR head sha.
2. `desk-req.sh <run-id> pm ci-status-main RUN_HOME/pm/ci-status-main.fields.json` writes `RUN_HOME/desk/<id>.req` and prints the `DESK` line. Exit 2 or 4: stop and report to the `pm` lead.
3. Send only after this start's `RUN_HOME/pm/outbox/register.consumed` exists (B1; the lead writes `outbox/register` at its start and the conductor renames it `register.consumed`, part-c C5.1). Check once when the request is ready: absent (or `register.refused`), send nothing; stop and report to the `pm` lead. Never wait unbounded. Backend `agent-tool`: send the exact `DESK` line by `SendMessage` to `desk` (B1 `DESK_ADDRESS`). Backend `claude-p`: write the line to `RUN_HOME/pm/outbox/<id>.desk`; the conductor relays it (B1, C5.2).

## Poll
- Poll `RUN_HOME/desk/<id>.out` (authoritative; a `DONE` line is advisory) up to 5 minutes; then re-send the same line once (same `<id>`, same `.req`). After 5 more minutes with no `.out`, or on `REJECTED <id> | sender` to an Agent-tool lead, apply the B1 no-reply rule: rename `<id>.req` to `<id>.req.noreply`, treat the request as terminal (`sender`), and the lead writes an escalation per part-c C2 `ESCALATE` with reason `human-step` (`RUN_HOME/pm/escalations/<unit>.md`; C2 does not define `<unit>` for a desk request, so this skill uses the desk `<id>` as `DEFAULT`, open owner question). Then stop and report to the `pm` lead.
- `REJECTED` with a terminal code (`sender|schema|hash|repo|policy`; `sender` also takes the no-reply path above): stop; the `pm` lead reports it to the owner; never resend, never another channel (B2.1, OP5 B).
- `REJECTED` with a curable code (`marker|order|stale-session|gate-missing|action-failed`): stop and report to the `pm` lead; a resend after the cause clears uses a fresh id (B2.1).

## Result
- For each name in the profile `merge_pipeline.stages[]`, read its `state` (`success|failure|pending|skipped|cancelled`, B6 "`state` as `ci-status`"; B6 reuses only the value set: the `ci-status` aggregate rule "a required `skipped` counts as `success`" is over `ci.required_checks[]`, not over `merge_pipeline.stages[]`). `skipped` is therefore not read as `success`: a `skipped` stage is a stop condition (open owner question; recommended answer: `skipped` is not `success`, so it fails a covered row and stops on an uncovered stage). `failure` and `cancelled` are not `success`. A name absent from the `.out` at the first read is handled as `pending` (the B6 aggregate's own reading of an absent check).
- Bound on `pending` or absent: if any stage is `pending` or absent, wait the profile `durations.ci_round_min` minutes (A.2.2), then request once more with a fresh id. A stage still `pending` (or absent) after that one round is a stop condition: stop and report the stage names to the `pm` lead. Never poll unbounded. INTERFACES gives no round count; one round is this skill's bound until the owner rules (open owner question).
- Staged file (skill-local, `DEFAULT`): the lead is the single writer of `RUN_HOME/pm/evidence/ci-status-main.stages`, one line `ci-status-main merge_sha=<PM_SHA> <stage>=<state> ... out=RUN_HOME/desk/<id>.out` from the last `.out`, including the E2E stage and the deployment check (B4). It is also the single writer of the `.line` of each stage-covered row (SKILL.md Step 1); no runner runs or writes those rows. The verify-tier verdict agent reads both (SKILL.md Step 10); the record's `## Merge pipeline` is copied from it.
- A stage covered by a plan row (the row's command is the `ci-status-main` read of that stage) decides that row: `success` passes it, `failure` or `cancelled` fails it, under the row's class (`skipped`: stop condition above).
- A stage that is not `success` and that no plan row covers: stop condition. Report the stage name to the `pm` lead so the human is informed (design part-03 §3.6 step 8 "an E2E-stage failure opens a fix unit and informs the human"); it cannot enter `new-units.md` because it has no plan row id (D2.2 row 12). Open owner question.
